# 深度拆解：什么是 Router（路由分发）多智能体架构？

当面试官听到你说出“Router 架构”时，他们会想知道你是不是真的懂底层的设计模式，还是只背了名词。

你可以用以下这套**“大公司组织架构”**的比喻来深入浅出地讲解。

---

## 1. 痛点重演：单体巨石 Agent 的“认知过载”

假设系统里有 15 个 API（查物流、改地址、退款、查商品参数、查优惠券...）。

**【以前的做法（单体 Agent）】**：
你把这 15 个工具的说明书（Function Schema），一股脑全塞给大模型。
当用户问：“我想退款，但我的地址之前填错了，能改吗？”
此时，大模型面前摆着 15 个按钮。它很容易产生**“选择困难症”**（认知过载），可能会把“退款”的商品 ID 错误地填进“改地址”的单号里，甚至直接崩溃报错。

这在工程学上叫：**工具箱过大导致的幻觉概率呈指数级上升。**

---

## 2. 解决方案：Router 架构（分而治之）

既然一个全能员工管不了这么多事，我们就把它拆解成**一个前台接待员（Router）+ 几个专业工程师（Sub-Agents）**。

### 核心设计：
我们不再把 15 个工具全部暴露给前端。我们做三组细分包：
*   **【售后 Agent】**：手里只有 4 个工具（查订单、改地址、退款、催发货）。
*   **【售前 Agent】**：手里只有 5 个工具（查库存、查尺码、商品参数对比）。
*   **【活动 Agent】**：手里只有 3 个工具（查优惠券、凑单计算）。

然后在最前面，放一个**【Router 路由 Agent】**。

### 工作流演练（面试必讲流转过程）：

1.  **用户进线**：“我昨天买的鞋子怎么还没发货？还有能不能把收货电话换一下？”
2.  **大路由决策 (Router)**：
    *   此时 Router 手里**没有任何具体的查订单 API**。它手里只有 3 个方向盘（前往售后、前往售前、前往活动）。
    *   Router 看了一眼用户的意图，瞬间判断出：“这是售后问题”。
    *   Router 执行它的唯一任务：把用户的话筒，丢给【售后 Agent】。
3.  **专家接管 (Sub-Agent)**：
    *   【售后 Agent】接管了对话。此时，它的视野里**只有这 4 个售后专用的工具**，绝不会受到“查尺码”这类售前 API 的干扰。
    *   因为上下文极其干净，模型轻而易举地做出了精准的 Function Calling：先调用 `get_order_status`，再调用 `modify_address`。

---

## 3. 面试升华：为什么 Router 架构是企业级 Agent 的终局？

在回答完技术过程后，作为 PM，你要拔高到**研发效能**和**系统扩展性**的层面。你可以这样说：

> “使用 Router 架构，解决的不仅仅是大模型的准确率问题（匹配准确率可从 60% 飙升至 95% 以上），更重要的是它解决了团队的**工程协作问题**。
>
> 如果是单体 Agent，15 个 API 耦合在一个超大 Prompt 里，售后团队想改个退款逻辑，很容易把售前团队的逻辑搞崩。
> 而采用 Router 架构后，售前、售后、财务线可以**各自独立维护自己的 Sub-Agent**。我要加一个新业务线？只需在 Router 的入口处加一个分支即可，底层系统实现了解耦（Decoupling）。这就是我认为 AI PM 必须懂架构设计的原因。”
