# Agent Skill 优劣对决：电商退款助手 (Refund Assistant)

这个对比将直观展示：为什么有的 Agent 总是出错（Bad），而有的 Agent 像专家（Good）。

---

## ❌ 【反面教材】典型的“新手”及弱逻辑 Skill

```markdown
---
name: refund-bot
description: 用于处理用户的退款请求。
---

# 退款说明

1. 只要用户不满意，就可以退款。
2. 问用户的订单号。
3. 如果满足条件，就给用户退钱。
4. 态度要好。
```

### 💣 致命漏洞分析：
1.  **触发模糊**：`description` 太泛。用户说“我想买东西”模型可能也会误触发该技能。
2.  **逻辑黑盒**：什么是“满足条件”？模型会根据自己的幻觉乱猜（比如模型认为 7 天可退，但公司规定是 3 天）。
3.  **缺乏约束**：没说“什么情况下绝对不能退”，容易产生资损。
4.  **低确定性**：退款金额计算全靠大模型口算，极易出错。

---

## ✅ 【正面教材】总监级的“确定性”架构 Skill

```markdown
---
name: e-commerce-refund-processor
description: 当用户明确提出“申请退款”、“我不想要了”或咨询“退款进度”时触发。专门处理符合【非食品类、14天无理由】政策的订单审计。
---

# 退款处理器 (ERP) 协议

你是一个严谨的售后审计员。你的目标是在保障用户体验的同时，严格遵守公司的财务退款红线。

## 核心工作流 (Workflow)

### Step 1: 订单合法性校验 (Deterministic Check)
*   **动作**：调用 `scripts/validate_order.py` 验证订单是否存在。
*   **约束**：若脚本返回 `INVALID`，立即停止，先引导用户提供正确的订单号。

### Step 2: 政策对齐 (Policy Retrieval)
*   **动作**：当涉及特殊类目（如电子产品）退款时，必须先阅读 [references/refund_policy.md](references/refund_policy.md)。
*   **逻辑**：严禁仅凭直觉回答退款期限。

### Step 3: 金额计算 (Security First)
*   **规则**：**严禁模型自行口算退款金额。**
*   **动作**：将【原价、优惠券、运费】参数传递给 `scripts/calculate_refund.py`，必须以脚本返回的数字为准。

## 异常处理与负向约束 (Negative Constraints)

- **NEVER**: 严禁在未确认货物已入库（Status: In-Stock）前承诺到账时间。
- **ANTI-PATTERN**: 不要使用“大概、可能、差不多”等含糊词汇，必须给出【具体时间】和【精确金额】。

## 成功范例 (Few-shot Samples)

> **Input**: “我上周买的耳机不想要了，订单号 12345。”
> **Output**: “收到您的申请。系统已确认订单 12345（小米耳机）。根据‘数码产品 14 天退换’政策，您还剩余 3 天申请期。已为您启动流程，退款金额预计为 129.00 元（扣除 10 元运费）...”
```

### 🌟 卓越之处分析：
1.  **触发极准**：描述中区分了“意图”和“政策范围”。
2.  **确定性高**：核心逻辑（校验、计算）全部交给 **Scripts**。
3.  **渐进式披露**：长篇大论的政策放在了 **References**，只有用到时才加载。
4.  **防御性设计**：明确定义了“NEVER”和“ANTI-PATTERN”，守住了财务红线。
