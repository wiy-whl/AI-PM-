# 高级架构理念：把“文件系统”作为 Agent 的极简上下文接口

在 AI Agent 开发中，最容易掉进的坑就是**“上下文填鸭”**：无脑把所有 API 返回的结果和工具说明，全部贴进给大模型的系统提示词里。

这篇文章萃取了目前顶尖代码编辑器 Cursor 的设计哲学：**默认少给，按需发现。(Dynamic Context Discovery)**。这正是你（作为高端 AI PM）在面试中用来降维打击的关键武器。

---

## 一、为什么“直接喂上下文”是劣质架构？

在你的量化因子挖掘项目中，Agent 每完成一次尝试，都会去调用回测接口。
* **初级做法的弊端**：回测接口会返回几百上千行的报错堆栈或交易明细 JSON。如果你把这坨 JSON 原封不动贴进大模型的对话框（Context Window），让它反思：
  1. 瞬间烧掉几千上万个 Token（极度费钱）。
  2. 乱七八糟的干扰信息会严重污染大模型的注意力流，导致反思能力降低。
  3. 这些报错信息会在历史对话里永久留存，拖垮后续的每一句对话速度。

---

## 二、架构进化：将“文件系统”作为缓冲层

在这个层级上，我们不再把数据直接喂给大模型，而是**用操作系统的文件作为沟通的实体媒介**。

### 1. 工具调用结果的物理隔离：写文件 vs 贴文本
*   **做法**：当回测端跑完后，不要把报错写进对话框。而是将这几十 KB 的报错直接保存为本地文件：`logs/alpha_01_error.json`。
*   **通信方式**：系统只给 Agent 的聊天界面发送一句话指令：“你的策略回测失败，最新报错快照已存放于本地 `logs/alpha_01_error.json`。”
*   **按需提取 (Dynamic Discovery)**：如果 Agent 真的想探究到底哪里错了，它可以运用它手里的 `grep` 或文件读取工具，自己写脚本去那个文件里抽离出关键的 3 行报错。如果不查，它就不会消耗任何 Token。
*   **好处**：这在物理上保持了上下文大盘的**绝对干净**。

### 2. 工具白皮书的“按需加载” (MCP 减免 46% 的开销)
*   如果你的量化平台有 50 个复杂工具。
*   不要在一开始把 50 个工具的所有参数定义全告诉大模型。
*   **做法**：把 50 个工具的名字列个短清单给大模型，它的具体用法存进本地的独立文件夹里。大模型看见名字后，如果觉得需要，再通过专门的指令自己去对应文件夹里读取具体的使用说明（Schema Definition）。

## 三、长会话的“有损压缩”与“防失忆”机制

当一个 Agent 连续挖掘了 3 天因子，对话长达千万字，上下文窗口必定爆炸。如何不漏掉关键信息？

1. **传统的糟糕做法**：硬截断（Hard Truncation），直接把头两天的聊天记录丢弃。这会导致彻底的灾难级失忆。
2. **顶尖的有损追溯做法**：
   * 在清理上下文窗口之前，后台程序自动把这 3 天的完整聊天记录，保存为磁盘上的一个持久化文本：`/history_archives/session_mar12.md`。
   * 然后将聊天窗口清零。并向新开的空窗口注入一行超级摘要：“你们之前围绕‘动量因子’进行了三天挖掘，详情已归档于 `/history_archives/session_mar12.md`。”
   * 如果 Agent 忘了一个关键代码，没关系，它可以自己去读这个 Markdown 文件，把丢失的记忆**重新捡回来**。

## 🎯 面试一击必杀总结话术 (PM 视角)

如果在面试时讨论到：**“你是怎么控制大模型 Token 消耗和幻觉的？”解决思路不能只停留在改 Prompt 上。**

你可以抛出这段高维度的工程思考：

> “很多人只会在横向的 Prompt 长度上做文章，而我倾向于在纵向的系统层级上做**『物理隔离』 (Physical Isolation)**。
>
> 比如在处理大规模工具回调（如回测报错 JSON）和长会话结转时，我不允许将这些数据直接排入宝贵且拥挤的模型 Context 内存带。我引入了 **『文件系统 (File System)』** 作为上下文交互的异步接口。
>
> 所有重型对象全部落盘保存为本地 `.md` 或 `.json`，只在上下文中给 Agent 提供指向文件的指针（Path）。这是一种基于 **『Dynamic Context Discovery (动态上下文发现)』** 的懒加载机制（Lazy Load）。它既实现了上下文的极度克制，省下了近半的 Token 冗余开销，又让整个过程成为了有损但可随时溯源读取的稳健架构。”
