# Agent Skill 架构深度解析：从物理组成到进化逻辑

在 Agent 领域，**Skill（技能）** 不仅仅是提示词的集合，它是 Agent 能力的“原子级扩展包”。它让模型能够从通用助手转变为具备“垂直领域确定性”的专家。

---

## 1. Agent Skill 的物理组成（四层架构）

你可以把一个高质量的 Skill 想象成一个**“带工具包的学习笔记”**：

### 第一层：SKILL.md (神经中枢)
*   **YAML Frontmatter (文件头)**：位于文件最顶部，夹在两个 `---` 之间。它是 Agent 的“身份卡”，包含 `name` 和 `description`。它是第一层触发机制。
*   **Markdown 指令**：紧跟在 YAML 之后的具体步骤、规则（Constraints）和逻辑。

### 第二层：Scripts (确定性执行器)
*   **定位**：针对那些对模型来说容易出错、逻辑脆弱、或重复性极高的任务（如复杂的数学计算、特定的文件转换）。
*   **价值**：变“概率生成”为“确定性计算”。

### 第三层：References (知识扩展库)
*   **定位**：存放长篇的文档、API 规范、领域知识。
*   **设计模式**：采用**渐进式披露 (Progressive Disclosure)**，只有在需要时才读取，避免挤占上下文（Context Window）。

### 第四层：Assets (产出模板库)
*   **定位**：存放标准的输出模板、Logo、配置 Boilerplate 等。

---

## 2. “渐进式披露”：优秀 Skill 的核心哲学

在设计 Agent 时，最忌讳的是把所有东西都塞进 System Prompt。

**高手的设计思路：**
1.  **Metadata (10% 权重)**：告诉 Agent：*“如果用户提到 A，你就看 SKILL.md”*。
2.  **SKILL.md (30% 权重)**：告诉 Agent：*“做 A 的步骤是 123，如果遇到复杂情况 X，去读 references/X.md”*。
3.  **References (60% 权重)**：详细的业务百科，只有用到时才加载。

---

## 3. 实战案例解析：`alpha-workflow-engineer`

这是系统自带的一个硬核 Skill，它展示了如何将复杂业务逻辑模块化：

*   **它的触发点**：当用户提到“挖因子”、“量化回测失败”时，`description` 准确捕捉任务。
*   **逻辑分层**：它没有在一段话里讲完，而是分成了 **7 个 Step**：
    1.  从数据集（Dataset）选型开始。
    2.  层层递进到 0-op, 1-op, 2-op 的设计。
    3.  最后到 Robustness 验证。
*   **约束机制**：明确规定了 **“Rule of 8”**（必须测 8 个变体）和 **“Logic First”**（逻辑先验）。

## 4. 如何构建一个“好”的 Agent Skill？(Checklist)

如果你在面试中被问到如何设计企业级 Skill，请引用以下四个标准：

- [ ] **确定性优先**：能用脚本跑的任务，绝不让模型瞎猜。
- [ ] **上下文极简**：SKILL.md 必须精简。每多 1000 个 Token 的冗余，模型的推理成本就更高，逻辑也更容易漂移。
- [ ] **防御性设计**：Skill 里不仅要写“怎么做”，还要写“什么绝对不能做”（Bad Patterns）。

## 5. Agent Skill 的优化路径 (Optimization Path)

优化一个 Skill，本质上是在做**“信噪比”**的提升。

### A. 触发精准度优化 (Trigger Accuracy)
如果系统在该用 Skill 的时候没用，或者不该用的时候乱用：
*   **动作**：优化 `description`。
*   **技巧**：包含具体的**“动词+名词”**和**“极端场景”**。
    *   *Bad*: “用于分析面试题目。”
    *   *Good*: “当用户提供面试题目、自己的回答以及面试官反馈时触发。通过分析逻辑漏洞、补充 AI PM 核心金词，将普通回答提升至‘总监级’水平。”

### B. 执行稳定性优化 (Execution Reliability)
如果 Agent 加载了 Skill 但输出不符合预期：
1.  **引入 Few-shot (示例对齐)**：在 SKILL.md 中加入 1-2 个高质量的 `Input -> Output` 范例。
2.  **强制 CoT (思维链)**：在指令中明确要求：*“在给答案前，请先写出你的分析思路（Analysis Chain）”*。
3.  **增设负面约束 (Negative Constraints)**：明确写出 **“ANTI-PATTERNS”** 或 **“NEVER DO”**。

### C. 性能与 Token 优化 (Token Efficiency)
如果 Skill 运行太慢或太贵：
*   **动作**：将复杂的文档、长篇案例移出 SKILL.md，放入 `references/` 文件夹。
*   **逻辑**：只有当 `SKILL.md` 的主逻辑判断有必要时，才引导 Agent 去读取 `references/`。

### D. 闭环验证 (Evaluation Loop)
*   **动作**：建立一个针对该 Skill 的**测试用例集**。

## 6. 写好一个 Skill 的“黄金法则”总览 (Master Checklist)

如果你要向上级汇报或在面试中总结，请记住这五个维度：

1.  **极简的描述 (Triggering)**：
    *   `description` 不是说明书，而是**“关键词诱饵”**。要包含明确的动词（分析、提取、验证）和应用场景。
2.  **确定性的内核 (Deterministic)**：
    *   **能用脚本，不用模型**。对于计算、比对、格式转换等脆弱逻辑，直接在 Skill 文件夹下配一个 Python 脚本。
3.  **渐进式的知识 (Progressive)**：
    *   **不要全量塞入**。主 SKILL.md 只放逻辑框架，大规模知识（如财务准则、法律条文）放入 `references/` 通过 RAG 或按需读取。
4.  **防御式的指令 (Defensive)**：
    *   必须包含 **Few-shot 例证**（给它一个满分答案参考）。
    *   必须包含 **Negative Constraints**（告诉它什么情况下绝对闭嘴）。
5.  **自我修正的能力 (Self-Correction)**：
    *   在输出中强制要求 **CoT (思维链)**。

## 7. 如何评估一个 Skill 的优劣？(Evaluation Framework)

在 AI PM 的面试中，你必须展示出一套**量化评价体系**，而不是感觉。

### A. 触发层指标 (Triggering Metrics)
*   **召回率 (Recall)**：该用 Skill 的时候，系统是否成功捕捉到了？（漏触发 = 系统没能力）。
*   **精确率 (Precision)**：没必要用的时候，是否误触发了？（误触发 = 浪费 Token，逻辑干扰）。
*   **F1-Score**：两者的综合平衡。

### B. 执行层指标 (Execution Metrics)
*   **指令遵循率 (Instruction Following Rate)**：模型是否严格遵守了“Workflow”和“Negative Constraints”？（比如：有没有口算金额？有没有在没核实前乱承诺？）。
*   **参数准确率 (Parameter Accuracy)**：调用函数/脚本时，参数填对了吗？（JSON Schema 解析成功率）。

### C. 工程层指标 (Engineering Metrics)
*   **TTFT (首字延迟)**：加载这个 Skill 导致的额外延迟是否在 500ms 内？
*   **Token 转化率 (Token Efficiency)**：Skill 的描述长度与产出价值的比值。如果写了 2000 字指令只为了一个简单的分类，那就是过度工程化。

### D. 业务层指标 (Business Metrics)
*   **确定性 (Determinism)**：在 100 次重复测试中，输出结果的一致性。
*   **资损/红线风险 (Safety)**：是否产生过违规回答或错误的金额计算。

---

### 💡 面试加分点：
> “我会建立一个 **‘Skill 评测沙盒 (Eval Sandbox)’**，包含 50 个 Bad Cases。每当团队修改了 `SKILL.md`，我们都会自动跑一遍回归，只有通过率（Pass Rate）提升了，才允许合并到 Production 环境。”

## 8. 落地实践：你会构建哪些工程组件？(Infrastructure Architecture)

如果我要在公司内部落地一套 Skill 评估体系，我会主导构建以下五个核心工程组件：

### 1. 黄金测试集仓库 (The Golden Set Repository)
*   **构成**：一个结构化的 JSON/CSV 文件库，包含 Input、Expected Skill、Expected Parameters。
*   **PM 动作**：我会牵头建立 **“Case 收集制度”**，通过分析生产环境日志，将每天排名前 10 的报错 Case 转化为测试。

### 2. 回归测试沙盒 (Simulation Sandbox)
*   **功能**：提供一个“断网、Mock 数据”的运行环境。
*   **逻辑**：当 Agent 尝试调用实操 Skill（如“发起退款”）时，沙盒不真正扣钱，而是模拟 API 返回成功/失败，确保 Agent 在各种错误状态下都有正确的闭环逻辑。

### 3. LLM-as-a-Judge (自动打标机)
*   **原理**：用一个更强、更贵的模型（如 GPT-4o）作为“面试官”。
*   **动作**：将待测模型的 Skill 调用结果喂给 GPT-4o，针对 **“是否命中政策、参数格式是否合规、语气是否专业”** 进行 1-5 分的自动化打分。

### 4. Skill CI/CD 准入网关 (CI/CD Gateway)
*   **集成**：将评估过程嵌入到代码合并阶段。
*   **红线规则**：如果新修改的指令导致黄金集的 **Accuracy（准确率）下降 1%** 或者 **关键负向约束失效**，则流水线自动驳回，严禁发布。

### 5. 可视化监控大盘 (Observability Dashboard)
*   **指标**：展示各版本 Skill 的实时触发分布图、平均响应时间（Latency）以及**“人工接管率”**。

## 9. 落地操作手册：从 0 到 1 构建评估体系 (Operational SOP)

如果你被要求明天就开始带队落地，以下是你的行动指南：

### 第一步：定义“黄金集” Schema (Data Modeling)
*   **动作**：拉上架构师，定义一张通用的测试表。
*   **关键列**：`Query` | `Target_Skill` | `Target_Params_JSon` | `Expert_Reference` | `Weight` (权重)。
*   **PM 细节**：确保包含“Bad Cases”（即模型以前答错过的内容），而不全是容易题。

### 第二步：部署 Mock 服务层 (Mocking Layer)
*   **动作**：让工程团队写一个简单的 Proxy（代理服务）。
*   **逻辑**：当环境变量 `ENV=EVAL` 时，所有 Skill 调用的外部接口（API）不发往真实后端，而是路由到一个本地的静态 JSON 文件库。
*   **价值**：确保测试是**幂等（Idempotent）**的，跑 100 次结果都一致。

### 第三步：配置“考官” Prompt (LLM-as-a-Judge Setup)
*   **动作**：编写一段极其严密的打分模型指令。
```markdown
## 指令
你现在的任务是评估一个 Agent 是否正确调用了 Skill。
## 输入
用户问题、模型生成的参数、正确答案参考。
## 评分项
1. 参数完整度 (1-5)
2. 逻辑幻觉检测（是否捏造数据）
3. 语气合规性
```

### 第四步：挂载 CI 脚本 (CI Automation)
*   **动作**：在 `.gitlab-ci.yml` 中新增一个 Job。
*   **逻辑**：
    1.  检测 `SKILL.md` 是否有变动。
    2.  若有，自动启动 `eval_runner.py`。
    3.  运行所有黄金集，并生成 `eval_report.json`。
    4.  对比旧版本的 `report.json`，若关键指标下降，直接退出并标记流水线失败。

## 10. 深度专题：LLM-as-a-Judge (自动打标机) 详解

在 AI PM 的面试中，如果你能把 **“自动打标机”** 的逻辑讲透，面试官会认为你具备在大规模生产环境下维护 AI 质量的能力。

### 1. 核心原理：相对智能优势 (Relative Intelligence)
*   **逻辑**：我们用一个 **“更强（Scaling）”**、**“更贵（Costly）”** 且 **“知识储备更深”** 的模型（考官），去评估一个 **“更轻、更低延迟”** 的业务模型（考生）。
*   **意义**：人眼评测一天只能看 50 条，LLM 打标机一小时能批改 10,000 条，效率提升 **200 倍**。

### 2. 三大评分维度 (Scoring Rubrics)

#### A. 政策命中度 (Policy Compliance) —— “对不对？”
*   **打分项**：Agent 是否准确引用了最新的公司红线策略？
*   **示例**：如果用户问“能不能退货”，Agent 漏掉了“包装损坏不退”的细节，Judge 会直接判零分。

#### B. 参数合规性 (Schema Alignment) —— “圆不圆？”
*   **打分项**：Agent 调用接口时，JSON 格式和字段类型是否完全匹配。
*   **价值**：这一步是自动化的，但加上 LLM 后，可以识别出 **“参数虽对但语义错误”**（如：日期写成了 2099 年）的隐性问题。

#### C. 语气专业度 (Persona & Tone) —— “像不像？”
*   **打分项**：是否符合品牌设定的“温暖、严谨、专家”人设。
*   **量化**：Judge 会根据“禁词表、语气词比例、金句覆盖率”进行 1-5 分的感性量化。

### 3. 工程实现逻辑 (Implementation)
1.  **输入构造**：将 `Query` + `Agent Output` + `Standard Reference` (黄金答案) 组合成一个超大上下文。
2.  **强制 JSON 输出**：要求 Judge 返回结构化结果：
    ```json
    {"score": 4, "reason": "参数正确但语气略显生硬", "fix_suggestion": "建议增加‘亲爱的同学’开头"}
    ```
3.  **反馈循环 (Feedback Loop)**：PM 拿到失败报告后，直接把 `fix_suggestion` 翻译成指令变更，完成 Skill 的闭环优化。

## 11. 进阶：如何把 LLM-as-a-Judge 做得更深？(Advanced Patterns)

在面试中，如果你能提到以下这些“避坑指南”和“进阶技巧”，能展现你对 AI 质量控制（Evaluation）的极致专业。

### 1. 评估模式：打分制 vs. 对战制 (SBS)
*   **点分制 (Point-wise)**：直接给一个模型打 1-5 分。
    - *缺点*：模型容易“手松”，不管答得怎么样都给 4 分。
*   **对战制 (Side-by-Side, SBS)**：给考官模型两个答案（A 和 B），问：哪个更好？
    - **优势**：这种方式能消除打分膨胀，结论更鲁棒。我会记录 A 胜过 B 的胜率（Win Rate）。

### 2. 考官的“偏见”处理 (Bias Mitigation)
*   **位置偏见 (Position Bias)**：考官模型倾向于认为排在前面的答案更好。
    - **处理**：我会把答案 A 和 B 调换位置再测一遍。
*   **长度偏见 (Length Bias)**：考官模型倾向于认为答得越长的越专业。
    - **处理**：指令中规定严禁因为字数多而加分，必须核对“信息增量”。

### 3. 人机共治 (Human-in-the-Loop)
*   **抽样审计 (Sampling Audit)**：每月抽取 10% 的自动打分结果由人工复核。
*   **一致性对齐 (Agreement Rate)**：如果人工评分和 LLM 评分的一致性低于 85%，需重新优化考官的 Prompt。

## 12. 实战指南：如何从 0 亲自构建一个评估 LLM？(Build Your Own Judge)

构建一个“考官”模型主要有两种路线：**提示词工程路线 (Prompt-based)** 和 **微调路线 (Fine-tuning)**。

### 路线 A：基于最强模型的 Prompt Judge (90% 企业的选择)
这是性价比最高的方案，通过指令让 GPT-4o 瞬间变成“领域专家”。

#### 1. 考官人设 (Persona)
赋予模型一个极具权威感的身份。例如：“你是一名资深的金融合规审计师，拥有 15 年证券从业经验。”

#### 2. 定义详细的打分量表 (Rubric) —— 极其重要！
不要让模型自己决定好坏。你要告诉它：
*   **5 分 (Excellence)**：完美调用 Skill，参数一个不差，语气极佳。
*   **3 分 (Half-baked)**：Skill 调对了，但参数写错了或漏掉了关键约束。
*   **1 分 (Danger)**：出现资损逻辑、捏造数据或严重的安全漏洞。

#### 3. 注入 Few-shot (样本对齐)
在 Prompt 里塞入至少 2 对 **“用户提问-模型回答-标准评价”**。模型会模范你的打分逻辑。

---

### 路线 B：微调专家级 Judge (Fine-tuned Judge)
如果你的业务非常专业（如医疗手术建议、超复杂的法律合同审计），GPT-4o 可能也判不准。

#### 1. 偏好数据收集 (Data Collection)
*   **做法**：让两个 Agent 同时回答同一个问题。
*   **标注**：让人类专家标注“为什么 A 比 B 好”。这叫 **Preference Pair（偏好对）**。

#### 2. 微调训练 (DPO/RLHF)
*   **目标**：把人类专家的判定逻辑，通过微调注入到一个更小、更快的模型（如 Llama-3-8B）中。
*   **收益**：微调后的小模型不仅跑得快，而且由于专门学习了业务准则，其打分一致性可能超过通用的 GPT-4。

## 13. 考官构建完后：如何开启“自动化进化”之路？(Post-Build Workflow)

构建完“考官”只是第一步，真正的价值在于如何让它进入你的**生产管线**。

### 步骤 1：集成到 CI/CD 流水线 (The Gateway)
*   **动作**：将考官脚本挂载到代码提交（Git Commit）环节。
*   **逻辑**：每当有算法同学修改了 `SKILL.md`，流水线会自动让“考官”批改 100 道黄金集题目。
*   **准入阀值**：如果准确率低于 95%，流水线直接红灯，禁止代码合入。

### 步骤 2：建立“坏 Case 自动捕获” (Auto-Capture)
*   **动作**：在生产环境配置监控，只要用户点击了“不喜欢”或给予差评。
*   **逻辑**：系统自动将该对话片段脱敏后，送入“考官”进行诊断。如果考官认为确实答错了，该 Case 自动升级为一条新的“黄金测试题”。

### 3. 构建“反馈循环”优化指令 (Loop Optimization) —— PM 核心动作
*   **动作**：每周导出一份“考官审计报告”。
*   **核心内容**：不要看分数，要看考官给出的 **“扣分点分析”**。
*   **执行**：PM 针对这些高频扣分点，针对性地修改 `SKILL.md` 的指令。比如考官说“模型总是漏掉退款限额”，PM 就在指令里加粗强调限额规则。

### 4. 人机对齐审计 (Human-in-the-Loop)
*   **动作**：每两周进行一次“考官审计”。
*   **逻辑**：抽取 100 条考官打过分的数据，由 PM 亲自审核。
*   **指标**：**人机一致性 (Agreement Rate)**。如果考官打分和 PM 打分不一致，说明“考官”本身也需要更新 Prompt 了。

### 5. 跨模型影子测试 (Shadow Test) —— 进阶
*   **动作**：让新模型、老模型、对照模型同时跑同一套题，由“考官”同时打分。
*   **收益**：在不切换流量给用户的情况下，你就能知道新版本是否真的变强了。
