# 技术深潜：长程 Agent 的双轨制与外置状态机实现指南

在高级 AI PM 甚至架构师的面试中，关于 Agent 自主度（Autonomy）的考察，很容易陷入“让它可以自己调更多 API”这种肤浅的回答。

真正的自主权，不等于盲目放权，而是**“建立足以支撑无限次崩溃重试的托底基础设施”**。这就要求你必须从单节点的大模型调用，迈向完整的软件工程架构。以下是这套架构在系统设计层面的“真刀真枪”落地细节：

---

## 一、双轨制架构设计 (Two-Agent Architecture)

为什么要区分两个 Agent 角色？因为它们的“寿命”和“职责”不同。把“运筹帷幄”和“搬砖写码”放在一个脑子里，必然导致内存溢出。

### 1. Initializer Agent：首脑（运行一次，立即裁撤）
*   **触发时机**：项目立项时，接到用户的极其模糊的任务指令。
*   **唯一 KPI**：将任务转化为物理世界可追踪的状态档案。
*   **具体产出**：
    *   生成初始的 `git commit`（建立回滚基线）。
    *   生成基础的环境脚本 `init.sh`。
    *   **最核心的：生成全局控制枢纽文件 `feature-list.json`**。
*   **特性**：一旦生成上述档案它就自我了断，**绝对杜绝**在这个 Session 里写任何一行核心业务代码，以此保证上下文在项目起步时是最纯净的。

### 2. Coding Agent：打工人（无状态，可随时复活）
*   **触发时机**：Initializer 死去后，由外部触发一个全新的 Session 拉起它；或者在上一个 Coding Agent 崩溃后被自动拉起。
*   **核心特性（无状态 Stateless）**：它不自带跨越多次任务的“记忆上下文”。对于每一个新的 Coding Agent，它眼前的世界就是它在这个瞬间读取到的本地文件。

## 二、状态外置化：`feature-list.json` 的强约束协议

**面试必考点：为什么不用 Markdown 写 TODO List？**
因为我们需要外围 Python 脚本能做到 100% 毫无歧义的解析和卡控，只有 JSON 能做到这一点。大模型一旦不按 JSON 规定的枚举值修改文档，外围脚本直接锁死大模型。

**标准状态机的 JSON 结构：**
```json
{
  "project_name": "量化因子挖掘闭环",
  "global_status": "in_progress",
  "tasks": [
    {
      "id": "T-01",
      "description": "搭建数据下载模块 fetch_data.py",
      "status": "completed", 
      "git_commit_hash": "a1b2c3d" 
    },
    {
      "id": "T-02",
      "description": "基于 T-01 编写数据清洗逻辑",
      "status": "in_progress",
      "dependencies": ["T-01"] 
    },
    {
      "id": "T-03",
      "description": "编写回测接口与评价指标",
      "status": "pending",
      "dependencies": ["T-02"]
    }
  ]
}
```

**脚手架强卡控制度（极其重要的工业级设计）：**
1.  **唯一推进原则**：在这个列表里，状态为 `in_progress` 的任务，在同一时刻**只能有 1 个**。防止大模型胡乱并行写代码导致交叉污染。
2.  **依赖锁死原则**：如果大模型产生幻觉，跳过 T-02 直接去修该 T-03 的状态为 `in_progress`。外部 Python 脚本在解析 JSON 时会直接截胡报错：“不满足前置依赖 T-02”，并将错误丢回给大模型让它反思。

## 三、跨会话的“无损复联”演示

面试里如何生动描绘“断点续传”？

> “假设我的 Coding Agent 因为执行超大回测导致机器 OOM（内存溢出）死了。对于传统单体 Agent，这项目就废了。
> 
> 在我的架构下：
> 1. 我的守护进程（Daemon）发现 Agent 死机，直接重启一个**全新的大模型会话**。
> 2. 系统强制向新模型注入 Prompt：**“项目突发中断，请读取当前的 `feature-list.json` 和最后一条 `git log` 重构你的世界观。”**
> 3. 新模型去读 JSON：发现 T-01 已 `completed`，T-02 正处于 `in_progress`。
> 4. 新模型去读 Git Log 和本地文件：发现 T-02 的代码写了一半。
> 5. **奇迹发生**：新模型瞬间把逻辑接缝上了：‘好的，我的任务是接着这行代码把 T-02 写完。’
> 
> 只要任务还在 JSON 里，只要 Git 代码还在，我们就能容忍 Agent 无限次中途死机。”

## 四、隔离慢速 I/O (不要让大模型空转思考人生)

高级业务中，“去云端下五年的股票行情数据”可能要跑十几分钟。

*   **初级做法**：大模型调用下载工具后，整个主对话循环（Message Loop）进入阻塞死等。如果超时（Timeout），大模型连带任务一起崩盘。
*   **高级架构师做法**：**异步发配与事件轮询**。
    *   工具调用：大模型决定下载数据，调用工具 `start_downloading(params)`。
    *   外挂接管：这个工具其实只干了一件事：开启一个后台静默新进程去下数据，并在本地扔一个标尺文件 `lock_downloading_in_progress`。
    *   大模型休眠：此时外围 Python 告诉大模型：“数据已发配至后台拉取，你可以先停止当前会话，不要消耗 Token 等待了。”
    *   事件唤醒：十几分钟后数据下好了，`lock` 文件被外部程序删除。外围脚手架再次激活大模型：“上一波数据已就绪至本地 `temp_data.csv`，请你继续推进进度条。”

**总结：真正的高级自主性，是以“外围极度严苛的工程脚手架（文件读写、事件流）”去对冲大模型与生俱来的“幻觉与状态不稳定”。**
