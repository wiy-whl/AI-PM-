## 🔝 项目一：AI-Agent 驱动的量化交易策略自动化生成闭环

### 1. 项目背景与 PM 视角
传统量化因子挖掘依赖人工或暴力遗传算法，产生的因子往往缺乏“经济学解释性”，容易陷入过拟合（Overfitting）。作为 PM，你的目标是利用大模型作为“大脑”，构建一个能够自我进化、且符合金融逻辑的自动化因子工厂。

### 2. 核心架构（面试必讲点）
- **Logic-First 提示词工程**：不再只是给模型数据集，而是要求它先写“经济学假说”。例如：“分析师预测修正往往具有动量效应，因为信息传递存在滞后。”
- **思维链 (CoT) + 反思 (Reflection) 闭环**：
  1. **Agent 1 (Generator)**: 基于假说生成代码。
  2. **Executor**: 异步调用 WorldQuant 回测接口。
  3. **Agent 2 (Reflector)**: 如果回测指标（Sharpe < 1.0 或 Correlation > 0.7）不达标，将回测日志回传，模型分析错误并修正。
- **异步解耦架构（核心技术亮点）**：利用消息队列解决“生成快、回测慢”的步调不一问题。

#### 架构结构拆解：
1. **生成端 (Generator)**：大模型每秒可输出一个策略草案，直接写入 `策略待测队列 (Pending_Queue)`。
2. **缓冲层 (Message Queue)**：作为流量泄洪池，防止瞬间大量 API 请求导致 WorldQuant 接口限流或系统崩溃。
3. **回测端 (Sim-Workers)**：多进程监听队列，根据并发限额逐一抓取策略调用接口，等待分钟级的回测结果。
4. **反馈环 (Feedback Loop)**：回测完成后，结果（成功指标或报错信息）推送到 `反馈队列 (Callback_Queue)`，由 Agent 读取并进行 Reflection（反思迭代）。

#### 为什么这是 PM 的加分项？
- **资源效率**：LLM 不用等回测，可以并行生成后续策略。
- **高可用**：即使回测接口挂了，生成的策略也会存在队列里，不会丢失。
- **可观测性**：PM 可以通过查看队列积压情况，直观判断“算力”对比“挖掘速率”的瓶颈在哪里。

### 3. 面试常见问题 (Q&A)

**Q1：如何解决大模型的“幻觉”产生的非法因子代码？**
**A**：我们建立了“三道防线”：
1. **语法级验证**：通过正则和 AST 解析，在提交前拦截不支持的运算符（如使用了不存在的 `decay_exp`）。
2. **逻辑层限制**：在 System Prompt 中强制约束嵌套层数（不可超过 5 层），防止模型通过暴力嵌套拟合噪声。
3. **反馈式修复**：Executor 报错信息（如权重过大、数据缺失）会自动转化成自然语言反馈给 Generator 进行定向修改。

**Q2：这个项目对业务的量化产出有什么实质提升？**
**A**：
- **效率**：原本一个量化研究员一天只能推演出 3-5 个逻辑，现在系统每小时能跑出 50+ 个经由初步逻辑验证的候选因子。
- **质量**：通过“逻辑先验”约束，生成因子的过拟合风险大幅降低，IS 到 OS 的衰减率从原来的 XX% 降到了 XX%。

## 🏦 项目二：高并发智能客服应用系统 (BERT + RAG)

### 1. 项目背景
解决企业客服成本高、LLM 知识更新不及时且容易乱回答（幻觉）的问题。

### 2. 核心设计：漏斗式意图识别策略
- **第一层 (Fast Path)**：使用轻量化 BERT 模型做高频、定式问题的极速拦截（低延迟、省成本）。
- **第二层 (Knowledge Path)**：对于复杂问题，触发 RAG（检索增强生成）。通过向量数据库检索私有知识片断。
- **第三层 (Human Path)**：如果置信度低于阈值，自动流转至人工坐席，同时生成摘要方便人工快速介入。

### 3. 面试常见问题 (Q&A)

**Q1：RAG 场景下的幻觉问题你是怎么处理的？**
**A**：我们使用了 **"Context-Grounding"** 策略。在评价 Prompt 中加强约束：如果检索到的文档中没有答案，模型必须回答“抱歉，暂未查到相关信息”，而不是自行发挥。同时我们引入了 **Faithfulness（忠实度）** 评测指标。

**Q2：既然 LLM 这么强，为什么还要保留 BERT 这种“旧”模型做意图识别？**
**A**：这是出于**性价比（ROI）**和**性能（Latency）**的综合考量：
- **成本（Cost）**：BERT 的推理成本不到 LLM 的百分之一。对于 80% 的高频简单问题，用大模型纯属“高射炮打蚊子”。
- **速度（Speed）**：BERT 的首字响应几乎是毫秒级，而 LLM 往往需要 1-2 秒。在意图识别环节，毫秒级的判断能让用户感觉到系统非常灵敏。
- **确定性（Determinism）**：BERT 作为分类模型，输出非常稳定；而 LLM 可能会因为随机性（Temperature）把简单的意图识别错。

### 2. 你必须读懂的核心代码逻辑

#### A. 因子挖掘中的“反思 (Reflection)”逻辑循环
**面试点**：如果面试官问“你是怎么让 Agent 变聪明的？”，你要提到**闭环反馈 (Closed-loop Feedback)**。
*   **代码逻辑伪代码**：
    ```python
    while retry_count < max_retries:
        expression = agent.generate(economic_hypothesis)
        result = simulation.run(expression)
        if result.is_passed():
            break
        else:
            # 核心：将失败原因回传
            feedback = f"回测失败：相关性为 {result.corr}，超过了 0.7 的阈值。请修改！"
            agent.reflect_and_regeneration(feedback)
    ```

#### B. RAG 项目中的“向量检索 (Vector Search)”流程
**面试点**：如何保证客服不乱说？
*   **逻辑流程**：
    1.  **Embedding**：将用户问题转化为 1536 维的数值向量（特征提取）。
    2.  **Top-K 检索**：在向量数据库里找最相似的 3 个知识片段。
    3.  **Rerank (重排序)**：对检索回来的 10 条结果进行精细化排序，选出最准的。
    4.  **Prompt 组装**：将这片段作为“参考资料”塞进 Prompt，强制模型只许根据资料回答。

#### C. 量化项目中的“异步执行 (Asynchronous)”逻辑
**面试点**：由于回测很慢，你怎么提高效率？
*   **架构逻辑**：使用 `celery` 或 `asyncio`。
*   **核心：** `Producer (生成者)` 把策略塞进 Redis `Task Queue`，`Consumer (消费者/回测Worker)` 异步监听。这样 Agent 就不需要原地等待回测结果，可以继续思考下一个策略。

#### D. BERT 意图识别：自制还是开源？
**面试点**：BERT 这种模型你是怎么拿到的？
*   **底座：从网上拿 (Pre-trained)**：我们会从 Hugging Face 社区下载预训练好的底座模型（如 `bert-base-chinese`）。这种模型已经学过了全世界的通用语言逻辑。
*   **语义：自己训练 (Fine-tuning)**：底座模型不懂“招行手机银行转账限额”这种业务知识。
*   **PM 动作**：我会牵头收集并标注 **5,000 - 10,000 条**行内真实的用户语料，并进行**意图分类打标**。算法团队用这些“私有数据”对开源 BERT 进行 1-2 天的微调（Fine-tuning）。
*   **结论**：这就是典型的“用开源的引擎，加自家的燃料”，性价比最高。

### 3. AI PM 必须挂在嘴边的“金词”
- **Tokens**：LLM 的“耗油量”，决定了成本和模型的记忆上限（Context Window）。
- **Temperature**：控制随机性。写量化代码要低（0.2），求严谨；写学习助手的讲解要高（0.7），求生动。
- **Latency (延迟)**：分为首字生成延迟（TTFT）和总时长。
- **Precision/Recall (精确率/召回率)**：

| 指标 | 形象比喻：捞鱼 | 核心关注点 | 极端情况 |
| :--- | :--- | :--- | :--- |
| **Precision (精确率)** | 你捞上来 10 条鱼，有 9 条是想吃的，1 条是草。得分 90%。 | **“抓得准不准”**。强调降低【假阳性/误报】。 | 为了不抓到草，你只抓 1 条百分百确定的鱼。精确率 100%，但漏掉一池子其它的鱼。 |
| **Recall (召回率)** | 池子里有 100 条好鱼，你捞上来 60 条。得分 60%。 | **“抓得全不全”**。强调降低【假阴性/漏检】。 | 为了抓全，你把一池子水连草带泥全抽干。召回率 100%，但里面全是垃圾。 |

#### PM 的业务决策：Trade-off (权衡)
- **医疗 AI (你的科研项目)**：必须 **Recall 优先**。漏掉一个肿瘤是人命关天的事。哪怕医生辛苦一点去排除干扰（Precision 低点），也绝对不能漏诊。
- **量化 Agent (你的项目)**：必须 **Precision 优先**。我们要的是“高质量因子”，如果 AI 推荐了 100 个因子但 90 个是废的，那是在浪费回测资源和交易资金。
- **F1-Score**：两者的平衡点（调和平均数）。当面试官问你“如果我要一个综合评价指标”时，回答 F1。
- **Zero-shot / Few-shot**：前者是“直接考”，后者是“给两个例题再考”。

## 附录：RAG 高级进阶与隐私保护 (Advanced RAG & Privacy)

在企业级 RAG 应用（如你的智能客服项目）中，面试官最关心的是“数据安全”和“检索精度”。

### 1. RAG 数据隐私解决方案 (Data Privacy)

**面试问题**：企业私有文档包含敏感信息，直接传给大模型会有泄密风险，你怎么解决？

*   **方案一：脱敏处理 (PII Masking)**
    *   在文档切片（Chunking）阶段，使用正则或 NER 模型识别出姓名、电话、卡号等信息，进行掩码或替换。
*   **方案二：向量库权限控制 (RBAC at Metadata Level)**
    *   在向量数据库中给每个 Chunk 增加权限 Meta 标签（如 `{"dept": "finance"}`）。检索时强制带上用户权限过滤条件，确保用户**搜不到**他不该看的文档。
*   **方案三：私有化部署 (On-premise)**
    *   使用私有 Embedding 模型 + 本地向量数据库（Milvus）+ VPC 隔离的大模型 API（如招商局内部的混元私有版），确保数据不出局域网。

### 2. 提升检索精度的“三板斧” (Advanced Tech)

**面试问题**：如果用户问得太模糊，模型搜不到正确答案怎么办？

1.  **混合检索 (Hybrid Search)**：
    *   **Keyword (BM25) + Vector (Dense)**。关键词搜索搜“专有名词”，向量搜索搜“语义场景”。两者加权（RRF算法）合并结果，精度比纯向量检索高很多。
2.  **重排序 (Rerank)**：
    *   向量检索是“海选”，速度快但不精。拿回 Top-10 结果后再用一个专门的 **Reranker 模型**（Cross-Encoder）进行二次精排，选出最相关的 Top-3 喂给模型。
3.  **查询重写 (Query Transformation)**：
    *   **Multi-query**：让 LLM 根据用户的一句话生成 3 个不同问法去搜。
    *   **HyDE (假设性回答)**：先让 LLM 瞎猜一个答案，用这个“假答案”去知识库里搜“真材料”。

### 3. RAG 效果评估指标 (RAGAS 框架)
- **Faithfulness (忠实度)**：回答是否来源于参考文档（防幻觉）。
- **Answer Relevance (答案相关性)**：回答是否直接解决了问题。

## 十二、 PM 高阶：如何定义北极星指标 (North Star Metric)

面试官问及指标时，考查的是你是否能穿透技术表象，触达**商业本质**。

### 1. 量化 Agent 项目
- **错误指标**：生成的 Alpha 总数（多而不精，全是噪声）。
- **北极星指标**：**IS-OS 性能一致性（Sharpe Ratio Decay Rate）**。
- **理由**：量化产品的核心价值在于“稳”。如果 AI 能生成 1000 个因子但 IS 跑出来的 Sharpe 在 OS（样本外）全部崩盘，那这个产品就是负价值。我们需要的是“逻辑先验”带来的确定性。

### 2. 学习助手 (MVP) 项目
- **错误指标**：日活 (DAU) 或 总刷题数（可能是用户在瞎点）。
- **北极星指标**：**次日留存率 (Day 2 Retention) 或 问题解决转化率**。
- **理由**：MVP 阶段在于验证“爽点”。用户今天用 AI 讲了一题，明天遇到难题是否还会第一个想到你？这决定了产品是否具备传播力和生命力。

### 3. RAG 智能客服项目
- **错误指标**：AI 回答总数。
- **北极星指标**：**人工转接率下降百分比 (Deflection Rate)** 或 **单次解决率 (First Contact Resolution)**。
- **理由**：客服系统的本质是“降本”。如果 AI 答了很多但最后用户都要求转人工，那 AI 只是增加了链路延迟，没有产生商业价值。

## 附录：模型部署与上线 (Model Deployment & Serving)

作为 AI PM，你需要决定模型“在哪里跑”以及“怎么跑”，这直接关系到用户体验（延迟）和公司成本。

### 1. 部署模式对比

| 模式 | 定义 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **云端部署 (Cloud)** | 模型跑在中心服务器（如 阿里云, AWS）。 | 算力强，支持大模型，易于维护更新。 | 延迟高（受网络影响），隐私风险，成本随调用量线性增长。 | 几乎所有 LLM/RAG 应用。 |
| **边缘/本地 (Edge/Local)** | 模型跑在用户终端（如 手机 NPU, PC GPU）。 | 零延迟，隐私性极高，无需支付 API 费。 | 算力受限（只能跑小模型），耗电量大。 | 手机翻译、简单的意图识别、隐私输入法。 |
| **私有化 (On-premise)** | 跑在企业内部局域网服务器。 | 数据绝对安全，符合金融监管。 | 初期硬件投入巨大（买卡贵），运维难度大。 | **银行/国企（如你实习的招商局）**。 |

### 2. 关键性能指标 (Deployment Metrics)

- **QPS (Query Per Second)**：每秒查询数。衡量系统的“并发承载量”。
- **RT (Response Time) / Latency**：响应时间。
    - **TTFT (Time To First Token)**：首字延迟。对 LLM 极其重要，决定了用户觉得“卡不卡”。
- **Throughput (吞吐量)**：单位时间内处理的数据量。
- **GPU Utilization (显存利用率)**：如果利用率低，说明你在浪费昂贵的算力资源。

### 3. 上线策略 (Release Strategy)

- **A/B Testing**：将 5% 的流量分给新模型，对比新旧模型的点击率、留存率等。
- **Canary Deployment (金丝雀发布)**：小流量上线，观察无报错后再全量推送。
- **Shadow Mode (影子模式)**：新模型接收真实流量但不给用户吐结果，只在后台对比新旧模型输出的差异。

### 4. 高阶：推理加速技术 (你不需要懂原理，但要听过名字)
- **Quantization (量化)**：把模型瘦身（如从 FP16 压到 INT8），速度变快但精度略掉。
- **TensorRT / ONNX**：模型的“加速外挂”。
- **VLLM / TGI**：目前最主流的大模型推理引擎框架。

## 附录：LLM 接口轮换与高可用机制 (API Rotation & High Availability)

在处理大规模并发（如你的量化 Agent 批量生成）时，单一 API Key 极易触碰 RPM/TPM（每分钟请求/Token数）上限。

### 1. 核心设计架构：API Pool 管理

**做法**：建立一个 **API 资源池负载均衡器 (Load Balancer)**。

- **轮询控制 (Round Robin)**：系统维护一个 Active API Key 列表，每次请求按顺序切换 Key。
- **权重分配 (Weight-based)**：根据不同账号的 Tier（级别）分配权重。比如企业版 Key 权重 0.8，普通版 0.2。
- **健康检查 (Health Check)**：自动检测被封禁或余额不足的 Key，将其移出可用池。

### 2. 异常处理：退避与切换策略

- **指数退避 (Exponential Backoff)**：当遇到 `429 Too Many Requests` 时，不立即重试，而是等待 2s, 4s, 8s... 逐渐拉长间隔。
- **自动降级 (Failover / Model Rotation)**：
    - 如果 GPT-4o 接口全线崩溃/达到限额，系统自动切换到 **Claude 3.5** 或公司自研模型作为备选，确保业务不中断（BCP 方案）。
- **断流熔断 (Circuit Breaker)**：如果某个 Provider 连续 10 次报错，锁定该 Provider 5 分钟，防止无效请求浪费用服务器资源。

### 3. PM 视角：为什么要设计轮换？

- **成本优化 (Cost Management)**：优先消耗低价 API 或已付过费的资源，超出后再走昂贵的高级模型。
- **SLA 保证 (Service Level Agreement)**：对于 24 小时运行的因子挖掘任务，系统稳定性（Uptime）高于单一模型的效果。
- **并发突破**：通过多 Key 轮换，将系统的总吞吐量翻倍。

### 5. PM 实战：如何在算力受限时平衡速度与并发？

当技术专家告诉你“显卡带不动”时，PM 应该从**业务流程**找空间：

- **路由分流 (Tiered Routing)**：
    - **逻辑**：80% 的用户问题是简单的（如：问候、查余额）。
    - **做法**：前置一个微型模型（如 BERT 或 7B 以下小模型）。通过意图识别，只有真的需要“深度推理”的问题才转发给 Llama-3，从而错峰释放算力。
- **语义缓存 (Semantic Cache)**：
    - **逻辑**：高频问题往往是重复的。
    - **做法**：在向量数据库前加一层缓存。如果用户问的问题与历史高频问题语义极其接近，直接吐出缓存答案，不经过模型推理。
- **感知管理 (UX Masking)**：
    - **逻辑**：用户怕的是“不理我”，不是“慢”。
    - **做法**：采用 **Streaming（流式传输）**。即便第一字延迟有 500ms，只要字一个个蹦出来，用户体感上就是流畅的。
- **服务降级 (Graceful Degradation)**：
    - **逻辑**：极端高峰期保证“能用”。
    - **服务降级 (Graceful Degradation)**：系统进入“简易模式”，暂时关闭复杂的 RAG 检索，直接返回基于意图识别的标准化回复。

## 附录：如何编写高质量训练数据 (Data Engineering for PM)

在 AI PM 的面试中，**“数据工程”**的表现往往比算法理解更重要。

### 1. 结构化格式：以 SFT (有监督微调) 为例
所有的训练数据都必须符合 **(Input, Output)** 的逻辑。

*   **JSON 格式示例**：
    ```json
    {
      "instruction": "你是一个考研政治辅导老师，请用大白话解释‘价值规律’。",
      "input": "什么是价值规律？",
      "output": "简单说，价值规律就是‘等价交换’。商品值多少钱由生产它花的劳动时间决定，价格会围着这个价值上下波动..."
    }
    ```

### 2. 数据来源：从哪儿弄来 2000 条数据？
1.  **真实语料 (Real Logs)**：从你回收的 300+ 份问卷和用户 1V1 访谈中，提取最真实的问题描述。
2.  **数据增强 (Data Augmentation)**：
    *   **同义改写**：让 GPT-4 把同一个问题改写成 10 种不同的问法（增加泛化能力）。
    *   **负样本构造**：故意造一些“超出口语、无关问题、政治敏感”的问题，教模型学会“拒答”。
3.  **合成数据 (Synthetic Data)**：用大模型根据知识图谱自动生成“问题-答案对”，但必须经过 PM 人工审核。

### 3. PM 的审核标准：什么是“金牌数据 (Golden Sample)”？
*   **准确性 (Accuracy)**：答案必须是业务 100% 正确的。
*   **格式一致性**：比如所有答案必须以“同学你好，...”开头，以“希望能帮到你！”结尾。
*   **难度梯度**：数据必须包含：容易题 (60%)、中等题 (30%)、极端长尾题 (10%)。
*   **去噪**：剔除掉错别字、无意义的语气词。
