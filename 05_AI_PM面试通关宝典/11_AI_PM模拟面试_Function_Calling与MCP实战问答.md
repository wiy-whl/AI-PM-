# AI PM 模拟面试：Function Calling 与 MCP 实战问答

以下是我以**大厂高级 AI 总监**的视角，针对 Function Calling 和 MCP 对你发起的 3 道“连环压力面试题”。这三个问题层层递进，从架构选型到性能瓶颈，再到极端情况处理。

---

### ❓ 问题 1（架构选型题）：混合场景下的技术决策

**面试官（我）**：
“我们现在要给电商事业部做一个售后 Agent。它既需要去公司的订单系统里查正在运输的物流状态，又需要去读一堆离线的 Word 版《退换货政策文档》。如果是你来统筹这个 Agent，在接入层，你会全部用 Function Calling、全部用 MCP、还是混合设计？为什么？”

**候选人（你）：**
“我会采取**混合设计（Hybrid Architecture）**。
对于查询《退换货政策文档》，我会坚决推行 **MCP 协议**。因为政策文档是非结构化的本地或云端文件系统，MCP 天生就是为了‘上下文挂载’设计的。我只需找一个本地文件系统的 MCP Server 插件，LLM 就能像挂载 U 盘一样直接读取它。如果用 Function Calling 去读文件，无论是切片流转还是 Token 截断，工程上都极其丑陋。

但对于查询订单状态，我会保留 **Function Calling** 机制。订单 API 是非常具体的行动（Action），比如输入 `order_id` 返回物流坐标。Function Calling 在这种‘小数据量、高频次、强 Schema 约束’的 API 调用上非常成熟。
所以我的总体架构是：**用 MCP 做知识上下文的挂载，用 Function Calling 做精准动作的执行。**”

---

### ❓ 问题 2（性能瓶颈题）：MCP 的隐藏陷阱

**面试官（我）**：
“你刚才把 MCP 说得很好，即插即用，不用写代码。那如果我现在找了一个 GitHub 的 MCP Server，然后把我们公司几十个微服务的海量代码库全通过 MCP 挂载给了大模型。你觉得系统上线后会遇到什么灾难性的问题？”

**候选人（你）：**
“会遇到可怕的**Token 爆炸和延迟（Latency）灾难**。
很多初级 PM 对 MCP 有个误区，以为‘挂载了’就等于大模型瞬间吸收了。但实际上，MCP 只是打通了通道，这几十个代码库的数据最终还是要变成 Token 塞进大模型的 Context Window（上下文窗口）里。
如果我们不做约束拦截，员工问一个宽泛的问题（比如‘帮我查一下登录报错’），MCP 可能会把几万行代码直接推给大模型。这不仅会导致单次对话成本高达几十块钱，而且模型推理时间可能长达两三分钟，用户体验直接崩溃。
**我的解法是**：即使上了 MCP，中间的网关层依然要做好 **RAG 的截断预处理**或者**显式的文件夹访问限制**，绝不能让前台的 Agent 无限制吞噬后台的 MCP 数据源。”

---

### ❓ 问题 3（风控与兜底）：MCP 真的安全吗？

**面试官（我）**：
“前面你提到了用 Function Calling 时，模型如果乱编参数会导致调用失败报错。那现在我们全面拥抱了 MCP，大模型可以直接通过 MCP Server 读写 Jira 甚至操作数据库了。你觉得 MCP 解决模型乱编参数的问题了吗？如果没有，作为 PM，你怎么设计安全底线？”

**候选人（你）：**
“**MCP 并没有解决 LLM 的幻觉问题，它甚至放大了风险。**
Function Calling 出错，大批量报错只是在网关层；但 MCP 如果开放了 Write（写入）权限，大模型可能因为理解错误，直接通过 MCP 发送了高危的数据库 Drop 命令，或者乱改 Jira 状态。

作为 PM，我部署 MCP 的第一天就会立下三条风控底线：
1.  **读写分离**：初期上线所有的 MCP Server，必须强制开启‘只读（Read-Only）’模式。绝不把核心系统的写入权交给纯自治的 Agent。
2.  **Human-in-the-loop (人类确认) 机制**：如果业务非要通过 MCP 执行写入动作（如关闭工单），当大模型构建完 MCP Tool Call 后，系统必须在界面上悬停，弹出一个包含具体参数的提示框，必须由员工点击‘Approve’后，代码才能实际执行。
3.  **细粒度的权限沙盒**：给 Agent 的 MCP 账号只能是最低级别的子账号，绝不使用超级管理员 Token。”
