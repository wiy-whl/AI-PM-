# RAG 技术细节拆解：PM 怎么防研发忽悠？

当我们谈论 RAG (Retrieval-Augmented Generation) 时，很多 PM 觉得那是“算法黑盒”。但在 `EvalLoop` 中，我为你手写了一个极简却完整的 RAG 系统（见 `rag_pipeline.py`）。

在面试中，如果你能讲清这三个核心组件，面试官会觉得你的技术底子极度扎实。

---

## 核心挑战：如何让不懂金融的 LLM，准确无误地背诵公司的审核规则？

### 步骤一：文档切片与“变成数字” (Embedding)

**技术动作**：把长篇大论的公司规章制度切成小块（Chunk），然后把每一小块塞给 Embedding 模型（如 `text-embedding-3-small`），模型会吐出一个包含成百上千个小数的**数字列表（向量）**。

*   **代码体现**：在我们的代码中，`DOMAIN_RULES` 里有 8 条规则，`get_embedding()` 函数负责把每条规则转化成一个包含 64 个浮点数的数组。
*   **PM 面试话术**：“为了保证检索粒度，我们在 RAG 中采用了**细颗粒度的切片策略**。我没有把整本《因子开发手册》灌入向量库，而是让研发将每一条规则独立成一个短小精悍的 Chunk 再进行 Embedding，这大幅降低了检索时的噪声。”

### 步骤二：空间中的“找邻居” (Cosine Similarity)

**技术动作**：当用户传入一个新的 Alpha 表达式（比如 `ts_std(close, 20)`）时，系统立刻将这句话也变成一个相同的浮点数数组（向量）。接着，系统会在高维空间里，计算这个新向量和知识库里所有的老向量之间的**“余弦相似度”（Cosine Similarity）**。

*   **代码体现**：`cosine_similarity(v1, v2)` 函数就是做这个的。它计算的是两个多维箭头的**夹角**，夹角越小（数值越接近 1），说明这俩语义越相关。
*   **PM 面试话术**：“传统的关键词检索解决不了‘苹果’和‘iPhone’是同一个东西的问题。我们 RAG 底层使用了语义 Embedding。基于**余弦相似度算法**，模型能聪明地发现一个使用了 `rank()` 函数的表达式，与规则库中关于‘权重分布审计’的规章在语义空间上距离最近。”

### 步骤三：Top-K 组装与喂给 LLM (Augmentation)

**技术动作**：拿着算好的相似度得分表，取出得分最高的 K 个（比如前 3 个）规则文本。然后把这 3 个规则文本**硬生生地拼接到用户的 Prompt 里面**，再发给执行审核任务的 LLM（gpt-4o-mini）。

*   **代码体现**：在 `call_candidate_model` 函数中，你会看到这一行：`context_text = "\n\n".join([...])`，这就是暴力拼接的过程。
*   **PM 面试话术**：“我们在系统里设定了 `Top-K = 3` 的超参。这意味着 LLM 每次做判断前，都会被‘强行灌输’最相关的 3 条公司规则作为上下文。这不仅**彻底干掉了大模型的幻觉**，而且由于送进去的 Token 只有短短几百个，相较于把整个规则库都扔给 GPT-4，我们的**单次调用成本下降了 90% 以上**。”

## 🎯 如果面试官问：RAG 如果搜不准，你作为 PM 会怎么办？

这就是经典的压力测试！千万不要说“我去催算法调参”。

**满分回答：**

> “RAG 搜不准，有 80% 的概率不是算法的锅，而是**数据基建**的锅。
> 我会立马检查三个点：
> 1.  **切片切坏了吗（Chunking）**？有没有把本来一段完整的话从中间劈成了两半？如果有，我会要求改用基于语义或固定标题的切分器。
> 2.  **源数据是垃圾吗**？如果连人工读了文档都找不到答案，Embedding 肯定也找不到。我会发起一次文档体检，清理掉过期、歧义模糊的规则文档。
> 3.  **加‘伪造问答’（HyDE）**。如果用户的搜索词太短（比如只搜了一个‘权重’），在找向量时容易偏。我会加一层小模型，先让小模型根据‘权重’瞎编一个答案，然后拿这个瞎编的答案（长文本，包含丰富上下文）去向量库里搜。这个技巧亲测管用！”
