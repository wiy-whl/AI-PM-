# AI PM 实战：如何解决 Function Calling 匹配度不高的问题？

在构建 Agent 时，Function Calling（函数调用）是模型连接外部世界的“手”。如果手不听使唤（经常调错工具、参数填错、或者死活不调用），应该如何从 PM 的视角进行优化？

这个问题在面试中是**极佳的加分项**，因为它直接考验了你对“Agent 工程上限”的理解。

---

## 核心诊断：为什么会匹配不高？
匹配不高通常有三个原因：
1. **工具描述太模糊**（模型不知道这个工具到底能干嘛）。
2. **参数名和用户意图有差异**（模型不知道对应的参数该填什么）。
3. **塞给模型的工具太多**（大模型也会“选择困难症”）。

---

## 🛠️ 优化四板斧 (The PM Playbook)

### 1. 优化 Tool Description（工具说明）—— 把描述当成 Prompt 来写
**错误做法**：“这是一个获取天气的工具。”
**正确做法**：“使用此工具查询指定城市的实时商业气象数据。**适用场景**：用户询问今天是否适合户外活动、航班是否可能延误时。**切勿使用此工具**查询历史天气数据。”
*   **面试话术**：“我发现导致 Function 调不准的最大原因是研发把工具描述当作代码注释来写。我作为 PM，接管了所有工具的 `description`。我会明确写出**‘何时使用’**和**‘何时禁止使用’（负向约束）**，这极大降低了模型的幻觉路由。”

### 2. 详细定义 Parameter Schema（参数说明）—— 避免“参数编造”
**错误做法**：`location (string): 城市名`
**正确做法**：`location (string): 需要查询的城市名称，必须采用标准的省/市格式（例如：中国广东省深圳市）。如果是海外城市，请直接使用英文全拼。`
*   **添加 Enum (枚举值)**：如果参数的范围是固定的，**必须使用 Enum**。比如 `order_status: Enum["PAID", "SHIPPED", "CANCELLED"]`，这样模型就绝对不会填错。

### 3. 提供 Few-Shot Examples（在系统提示词中打样）
当工具有点复杂时，光靠描述是不够的，要在 `system_prompt` 里直接给模型演示。
*   **面试话术**：“对于复杂的组合操作，比如既要调天眼查，又要调财务工具。我会在主 Prompt 里放 2 个黄金示例（User 问什么，先调 A 再调 B）。模型有了模仿对象，Function Calling 的匹配率能从 60% 飙升到 90% 以上。”

### 4. 动态路由与分层架构（Agentic Router）
当你手里有 50 个工具时，一股脑全扔给当前节点，模型一定会匹配错。
*   **面试话术**：“当工具超过 10 个时，匹配准确率会断崖下跌。我的解法是**‘分工架构’（Multi-Agent）**。我会在前面放一个 Router（路由）Agent，它手里只有 3 个大工具（查询、下单、售后），它先判定方向。判定去‘售后’后，再把任务交给专门的‘售后 Agent’，它手里有 5 个细分的售后 API。通过**限制单节点的工具数量**，从根源上解决了匹配混乱的问题。”

---

## 🛡️ 兜底策略：如果还是调错了怎么办？

**“自反思循环” (Reflection Loop)**
*   **面试话术**：“任何模型都会出错。我设计的 Agent 不仅仅是单次调用，我还引入了 Error Handle 机制。当 API 报错‘参数不合法’时，我们的 Agent 必须把报错信息连同当初自己写的规划**再喂回给 LLM**，让 LLM 根据报错自己修正参数重新调用。这就叫拥有**一定自治能力**的智能体。”
