# AI PM 核心概念必修课：Function Calling vs. MCP (模型上下文协议)

在面试中经常会被问到：“大模型是怎么调用外部工具的？” 
传统的答案是 Function Calling，但在 2024 年底之后，**MCP (Model Context Protocol)** 成为了构建 AI 应用的最前沿标准。能讲清这两者的本质区别，说明你的架构视野非常超前。

---

## 🧩 第一部分：什么是 Function Calling (函数调用)？

**【一句话定义】**
大模型本身不能上网、不能查数据库，Function Calling 是 OpenAI 搞出的一套“代办机制”，让大模型可以**“输出一段 JSON 格式的请求”**，指挥外部系统去干活。

**【大白话比喻：老板与秘书】**
*   老板 (大模型本身) 坐在办公室里，没有网线，也没有腿。
*   你问老板：“今天深圳天气如何？” 
*   老板不知道，但他知道自己有个叫 `get_weather` 的秘书工具。
*   于是老板给你递了个小条子（JSON 格式）：`{"tool": "get_weather", "location": "深圳"}`。
*   **注意！真正去跑腿查天气的是你的代码（外部系统），不是大模型。** 你的代码查到结果（晴天，25度）后，把小条子递回给老板。
*   老板拿到结果，再用人话回复你：“深圳今天是晴天，25度。”

**【PM 视角的局限性】**
*   **累死程序员**：每加一个新工具，研发都要在代码里手写一遍 API 对接逻辑。如果公司有天猫、京东、拼多多 3 个电商平台的订单查询接口，研发要写 3 遍 Function Calling 适配代码。
*   **不通用**：OpenAI 的 Function Calling 格式跟 Claude 的格式、开源 Qwen 的格式都有细微差异，跨模型迁移成本极高。

---

## 🌐 第二部分：什么是 MCP (模型上下文协议)？

**【一句话定义】**
MCP (Model Context Protocol) 是由 Anthropic (Claude的母公司) 提出的一种**开源标准化协议**，它就像是 AI 时代的 "USB 接口"，让大模型可以通过一套统一的标准，直接连通本地文件、公司数据库或第三方 SaaS 平台。

**【大白话比喻：万能转换插头】**
*   以前（Function Calling 时代）：你想给手机充电（让大模型接入新数据），到了英国得买英标插座，到了美国买美标插座（为每个数据源定制开发工具）。
*   现在（MCP 时代）：MCP 提供了一个**“万能 USB 插线板”**。不管是 Github 的代码、Jira 的工单、还是本地的 SQLite 数据库，只要数据方提供了一个符合 MCP 标准的插口（MCP Server），大模型大旗一挥（MCP Client），咔哒一声直接插上，瞬间就能读取所有数据并执行操作。

**【为什么 MCP 是一场革命？】**
它剥离了“大模型厂商”和“数据提供商”之间的强绑定。
作为 PM，你不再需要求着研发去一行行写 API 对接代码。只要飞书官方出了一个“飞书 MCP Server”，任何支持 MCP 的大模型（无论是 Claude 还是未来的 GPT）都可以直接读取飞书文档。

---

## 🥊 第三部分：核心区别对比 (面试必背)

| 维度 | Function Calling (函数调用) | MCP (模型上下文协议) |
| :--- | :--- | :--- |
| **设计本质** | 是一种**功能** (Feature)，是告诉模型“去调用这串代码”。 | 是一种**架构协议** (Protocol)，是让模型与数据源建立标准通信通道。 |
| **开发成本** | **高**（“点对点打洞”）。需要 PM 提需求，研发手写对接逻辑，换个模型或系统就要重写。 | **极低**（“即插即用”）。只要数据源有 MCP Server，就能无缝接入任何 MCP Client 生态。 |
| **适用场景** | 适合**简单的、一次性的 API 调用**（查天气、发个邮件）。 | 适合**大规模上下文注入、双向数据读写**（读取整个代码仓库、跨多个 SaaS 平台联动）。 |
| **生态站位** | 大模型厂商控制生态（比如都在适配 OpenAI 的格式）。 | 第三百方开源标准，打破厂商“数据孤岛”霸权。 |

## 🎯 面试实战演练（PM 高光话术）

**面试官**：“我们要给公司的 Agent 接入 Jira、Confluence 和内部财务系统，你觉得架构上该怎么设计？”

**你（拉高唯度反杀）**：
> “如果是以前，我可能会要求研发团队基于 **Function Calling**，去逐一阅读 Jira 和 Confluence 的 API 文档，为每个接口手写 Tool 函数。但这种‘点对点烟囱式’的对接，后期维护成本极高。
> 
> 现在我会主推基于 **MCP (模型上下文协议)** 的架构演进。我会要求团队直接部署开源的 Jira MCP Server 和 Confluence MCP Server。这不仅能让我们的 Agent 实现真正的**‘即插即用 (Plug-and-Play)’**，而且无论我们未来底层模型是从 OpenAI 切换到 Claude 还是本地开源模型，前端的数据接入层都无需重写。
> 
> **作为 PM，与其给模型造轮子，不如给模型通‘自来水管 (MCP)’。**”

---

这个回答将向面试官展示，你不仅不是一个只懂画原型的产品经理，还是一个时刻关注最新技术范式（MCP 是近期最火的 AI 概念），并懂得用架构思维解决业务降本增效的高阶玩家。
