# 外科级精讲：AI 代码助手"评测体系全流程"逐步拆解

> **核心定位**：你不是在测试软件，你是在为 AI 插件建立**"生产力保证书"**。每一步都必须带出你作为 PM 的决策逻辑，而不只是执行动作。

---

## Phase 0：开始之前——为什么要建评测体系？（定义问题）

在写第一道评测题之前，你需要讲清楚**"没有评测体系时，公司在经历什么痛苦"**。

**你的话术（问题诊断）：**
> "当我加入团队时，我们的 AI 编程助手刚刚接入腾讯混元大模型，处于早期内测阶段。当时团队判断模型好坏的方式，是靠算法同学手动感受，或者等用户在群里抱怨。
>
> 这带来了三个致命问题：
> 1. **迭代盲飞**：每次更新 Prompt 或换模型版本，大家不知道效果变好了还是变坏了。
> 2. **沟通耗散**：产品说"模型笨了"，算法说"你感觉不对"，争论没有数据支撑。
> 3. **问题定位失焦**：用户抱怨"代码出错"，但我们不知道是 RAG 检索出了问题，还是模型本身的问题，还是 Context Window 塞错了东西。
>
> **所以，建立评测体系的根本目的是：把 AI 插件的质量从『口感问题』变成『数字问题』。**"

## Phase 1：定义"什么叫好"——北极星与护栏指标设计

**这一步最重要，PM 的价值在这里体现。**

你不能让算法去定义好坏，因为他们定义的是"模型准得高"；你要从用户和业务出发，定义真正有意义的指标。

### 1.1 确立北极星指标：为什么是「代码采纳率」？

**你的话术：**
> "在评估各种可能的指标后，我最终将**『代码采纳率 (Acceptance Rate)』**确立为北极星指标，分为『按次采纳率』和『按行采纳率』两个子维度。
>
> 我选择这个指标的逻辑是：它是一个**『真实用户投票』**。用户按不按 Tab、涉不涉及采纳，反映的是他是否认可 AI 的这次输出。这比任何实验室分数都更接近真实价值。
>
> 但我同时意识到北极星指标有一个*盲区*：如果模型把一行无关紧要的代码写得完全准确，用户可能会采纳，但这不代表它有用。
>
> 所以我在北极星指标旁边额外设立了**『护栏指标 (Guardrail Metrics)』**——包括：首字延迟（TTFT，超过 400ms 就影响用户耐心）、单次采纳代码行数（防止 AI 只补全空格和注释来刷采纳率）。
>
> **这两个护栏指标的存在，让北极星指标变得真正有意义。**"

### 1.2 评测集指标 vs 线上指标的映射

**你的话术：**
> "我设计的核心原则是：**线下评测集的指标，必须能够预测线上的北极星指标变化**。
>
> 否则，你就是在做和产品无关的学术实验。
>
> 基于这个原则，我建立了一个简单的映射关系：
> - **Pass@1（编译通过率）** → 预测『按次采纳率』
> - **平均每次采纳行数** → 预测『按行采纳率』
> - **RAG 召回准确度** → 预测跨文件引用场景的采纳率
>
> 我每次跑评测集后，都会将实验室分数与后台看板的线上指标进行对比。如果两者变化趋势一致，说明我的评测集是有效的；如果出现背离，我就需要去补充新的 Case 来修正评测集的覆盖盲区。"

## Phase 2：构建评测数据集——从"写题"到"采矿"

**这一步要展现你的数据获取能力和产品嗅觉。**

### 2.1 数据来源的"三驾马车"设计

**你的话术：**
> "我没有坐在那里凭空想 500 道题。我建立了**三个数据源渠道**，每个渠道服务不同的目的：
>
> **渠道一：真实战场（占 40%）——从后台监控中挖掘"失败现场"**
> 我拉取了后台数据中，代码采纳率最低的那批生成记录。这些是模型表现最差的地方，也是最有价值的评测题来源。比如我发现，当用户在处理集团内部的 RPC 框架接口时，采纳率会跌到 30% 以下。我提取了这批代码片段，做脱敏处理后，直接转化为评测集的核心题目。
>
> **渠道二：专家知识库（占 30%）——利用 AI 辅助生成变体**
> 针对我们希望测试的核心能力（比如：正确处理 Java 的泛型、Python 的多继承），我用 Hunyuan 和 Claude 作为『题目生成器』，基于一个种子题扩展出 10 个覆盖不同边界条件的变体。这让我用 50 个种子迅速扩展到了 500 道多样化的题目。
>
> **渠道三：对抗红队（占 30%）——专门刺探模型的幻觉边界**
> 我设计了一批『陷阱题』，比如要求模型调用一个内部存在但拼写稍有偏差的私有工具函数名称，看模型是否会产生幻觉。这批题的价值不在于考察模型对不对，而在于**摸清模型在什么情况下会自信地撒谎**。"

### 2.2 数据标注的"三级分层"系统

**你的话术：**
> "光有题目不够，我需要让每道题都成为'可检索、可分析'的单元。我使用 LabelStudio 做了多维标注，分为三个维度：
>
> **维度一：上下文深度**（这是最重要的分层）
> - **L1 单文件局部**：模型只需要理解当前光标附近的代码就能回答
> - **L2 跨文件引用**：需要理解隔壁的类定义或接口文件（正是 RAG 最难的地方）
> - **L3 复杂重构**：模型需要理解一段业务逻辑，并完成多步骤的改造
>
> **为什么要这样分层？** 因为当总体 Pass@1 下降时，我第一时间通过维度筛选就能知道：是 L1 下降（说明基础模型变差了）还是 L2 下降（说明 RAG 检索出问题了）。直接排除了大量无效的沟通。
>
> **维度二：语言和场景**：Java/Python/JavaScript，以及补全/修复/生成三种任务类型。
>
> **维度三：难度系数**：简单（单行补全）、中等（块级生成）、困难（业务逻辑重构）。"

## Phase 3：自动化判分——如何客观评价"代码"？

### 3.1 三级判分的具体工作原理

**你的话术（完整版）：**
> "这是整个评测体系中技术含量最高的部分，也是我作为 PM 必须和算法、测开最深度协作的地方。
>
> 我设计了一个**三级阶梯判分体系**，每一级的成本和精度都不同：
>
> **第一级：执行级判分（最客观）**
> 对于有明确正确答案的题目，我要求评测集附带一个隐藏的 `assert` 断言。将 AI 生成的代码连同断言，提交到一个隔离的 CI 环境中执行。退出码为 0 即为 Pass，否则为 Fail。这不需要任何人工判断，是绝对客观的标准。
>
> **第二级：文本相似度判分（成本低，用于批量跑测）**
> 对于不容易写断言的补全类题目（比如：帮我续写这个函数的注释），我们计算 AI 输出与标准答案之间的 Levenshtein 编辑距离。我设定的阈值是 **80% 相似度**，低于这个值视为失败。
>
> 这里有一个重要决策：这个 80% 是怎么来的？我对 200 道题进行了人工复核，反复调整阈值，找到了『人类认为及格』与『算法阈值』的最佳交叉点。这是一个需要产品感觉介入的环节，不能纯粹靠工程师。
>
> **第三级：关键词与规则判分（专门针对安全红线）**
> 对于幻觉检测和合规拦截，我使用正则匹配。比如：如果 AI 输出的代码中包含了我们预设的『不存在的内部 API 列表』中的任何一个函数名，直接判 0 分；如果用户的指令包含越权关键词（比如涉及数据库直接写操作），而 AI 没有拒绝，也直接判 0 分。"

### 3.2 API 调用层的设计考量

**你的话术：**
> "在批量跑测时，我需要考虑几个工程上的实际问题，即便作为 PM 我不亲自写代码，我也必须想清楚这些：
>
> - **`Temperature` 设定**：评测时我将其设为 **0.1**（极低随机性），这样每次跑同一道题，结果是可复现的，评测结果才有对比意义。
> - **API 限速处理**：腾讯混元内网 API 有并发限制，批量跑测时容易触发 429 报错。我要求测开在调用脚本里加入指数退避（Exponential Backoff），确保 1000 道题能够稳定跑完，不因为网络抖动报错而中断整批测试。
> - **延迟监控**：每次 API 调用都要记录『从发出 Prompt 到收到第一个 Token』的时间（TTFT）。如果评测时发现某类题的 TTFT 特别高，说明那类 Context 组装方式给模型带来了很大的理解负担，这本身就是一个优化信号。"

## Phase 4：结果应用——评测集如何驱动产品迭代？

**这一步是体现你作为 PM、而非 QA 工程师的核心价值。**

**你的话术（完整版）：**
> "跑完评测只是第一步。我的评测体系真正的价值，在于把报告转化为行动。
>
> 我建立了一个简单的**『问题→归因→处方』流水线**：
>
> **举一个真实案例：**
> 我在某次评测中发现，L2（跨文件引用）场景的 Pass@1 从 68% 跌到了 52%。
>
> 第一步，我进行**归因分析**：
> 我去看后台的知识库看板，发现RAG 的『召回准确度』曲线在同一时段也出现了下跌。这说明与其说模型变聪明了，倒不如说它拿到的参考资料变差了。
>
> 第二步，我下钻到具体 Bad Case：
> 我把 Pass@1 从 1 变为 0 的那批题导出来，发现它们的共同点是：全都涉及最近两周新增的内部工具库。结合知识库看板数据，我推断问题是向量索引的**更新延迟**——新代码进了仓库，但还没有被重新 Embedding 到检索数据库里。
>
> 第三步，我给研发提出了**可执行的处方**：
> "建议将知识库的索引更新频率从每周一次提升到每天一次，并针对新增文件做增量索引，而不是全量重建。" 同时我量化了收益预期："如果 L2 场景 Pass@1 能回到 68%，根据线上指标的联动规律，我们的『按行采纳率』应该会提升约 3-4 个百分点。"
>
> 以上这个案例，展示了评测集不只是一个测试工具，而是**连接线下模型能力与线上用户体验的桥梁。**"

## 精华总结：3 句话搞定面试开场白

**适合在 1 分钟内自我介绍时使用：**

> "在招商金融的 AI 代码助手实习中，我认识到这款基于腾讯混元的插件在初期最大的问题是**质量黑盒**——没人知道它到底好不好、哪里在变好、哪里在变差。
>
> 我的核心贡献是建立了内部首套**『三层评测体系』**：用 Pass@1 编译通过率评估逻辑准确性，用 Levenshtein 编辑距离评估补全贴近度，用正则规则评估幻觉风险。配合后台看板的线上采纳率指标，我在每一轮评测后都能给算法和研发开出**精准的优化处方**。
>
> 这套体系最直接的产出，是将本来靠直觉驱动的迭代，变成了**数据闭环驱动**的产品进化。"
