# AI 产品经理必备：大模型评测体系深度指南

在 AI PM 的面试中，"评测体系"是区分一个 PM 是"调包侠"还是"架构师"的关键指标。

## 一、 评测的核心架构
一个完整的评测系统通常由 **输入库 -> 执行引擎 -> 评估机制 -> 反馈回路** 四部分组成。

### 1. 输入库 (Dataset)
- **基准测试集 (Benchmark)**：
  - **通用集**：如 MMLU, GSM8K (证明模型通用智力)。
  - **垂直集**：根据项目定义的专属语料（如你实习时的代码插件测试集）。
- **Case 类型**：
  - **P0级 Case**：红线问题、高频场景（100% 必须正确）。
  - **长尾 Case**：少见但复杂的问题（体现差异化竞争力）。

### 2. 评估机制 (Scoring)
- **客观指标 (Objective)**：
  - **代码类**：Unit Test 通过率, Pass@1。
  - **文本类**：Exact Match (针对固定格式), ROUGE/BLEU (现已不常用)。
- **主观指标 (Subjective)**：
  - **LLM-as-a-Judge**：定义评分标准（Prompt），让 GPT-4 充当裁判。
  - **维度权重**：正确性(40%)、逻辑性(30%)、安全性(20%)、简洁性(10%)。

## 二、 RAG 专项评测（针对你的智能客服项目）
RAG 产品的评测通常关注 **"三元组"**：
1. **Context Relevance (检索相关性)**：检索出来的知识片断是否真的能回答用户问题？
2. **Faithfulness (忠实度)**：模型给出的回答是否完全基于检索到的知识？(防幻觉)
3. **Answer Relevance (答案相关性)**：回答是否直接解决了用户的问题？

## 三、 如何从 0 到 1 搭建私有 Benchmark (PM 实战)

作为 PM，构建私有 Benchmark 的过程其实就是**“定义何为正确”**的过程。

### 1. 场景抽样 (Sampling)
- **数据来源**：线上 Log、专家手动编写、用户反馈中的 Bad Case。
- **分布设计**：按照业务权重划分比例（如：金融代码场景下，20% 属于数据库操作，30% 算法逻辑，30% 框架调用，20% 合规检查）。

### 2. 标准制定 (Ground Truth)
- **定义金标**：给每条输入数据匹配一个“专家通过版”的答案。
- **标注说明 (Guidelines)**：写一份详细的标注文档（给 LabelStudio 标注团队用），明确什么情况下打 1 分，什么情况下打 5 分。

### 3. 评测框架选择 (Tools)
- **自动化工具**：如果是代码，使用编译检查 + 单元测试；如果是文本，使用 **LLM-as-a-Judge** (由强模型打分)。
- **提示词工程 (Eval Prompt)**：精心设计用于打分的 Prompt，让模型给出评分及其**理由**。

### 4. 数据分布矩阵
| 维度 | 比例 | 难易度分布 (简:中:难) | 目标指标 |
| :--- | :--- | :--- | :--- |
| 代码补全 | 40% | 2 : 5 : 3 | Pass@1 > 65% |
| Bug 修复 | 30% | 1 : 4 : 5 | 修复成功率 > 50% |
| 系统理解 | 30% | 3 : 4 : 3 | 幻觉率 < 10% |

## 五、 评价 Prompt (LLM-as-a-Judge) 实战

### 1. 什么是评价 Prompt？
评价 Prompt 是你写给“裁判大模型”（如 GPT-4o）的一份**评分细则**。它告诉裁判：看到什么样的输入和输出，应该打几分，以及打分的理由。

### 2. 评价 Prompt 长什么样子？(以代码补全为例)

```markdown
# Role
你是一名资深的 Java 架构师，负责对初级程序员编写的代码进行质量审计。

# Task
请对比 [Ground Truth] 和 [Model Output]，对代码的【正确性】和【安全性】进行打分（1-5分）。

# Criteria
- 5分：逻辑与原答案完全一致，且考虑了边界错误处理。
- 3分：核心逻辑正确，但代码冗余或存在微小隐患（如资源未关闭）。
- 1分：编译不通过，或存在严重安全漏洞（如 SQL 注入）。

# Inputs
- [Input]: {user_query}
- [Ground Truth]: {standard_answer}
- [Model Output]: {model_generated_code}

# Output Format (JSON Only)
{
  "score": "int",
  "reason": "text",
  "suggestions": "text"
}
```

### 3. 为什么它很有用？
- **客观度过高**：像 `Exact Match` 这种规则，只要模型多写一个空格就算错，太死板。评价 Prompt 能理解“语义一致性”。
- **可复解释性**：它要求裁判模型给出 `reason`。当算法同学问“为什么我这版扣分了”，PM 可以直接把理由甩给他们看。
- **低成本大规模**：人工看 500 个 Case 要两天，评价 Prompt 跑一遍只要 5 分钟几块钱。

## 六、 核心术语深度解析

### 1. 标注文档 (Annotation Guideline)
**定义**：这是 PM 写给标注人员（人或裁判模型）的“阅卷标准准则”。
**作用**：防止不同的人对同一个答案有不同的评分标准，确保评估结果的**一致性 (Consistency)**。
**包含内容**：
- **打分范围**：1-5 分还是 0/1 分？
- **边界 Case 处理**：如果代码逻辑对了但格式乱了，扣几分？
- **具体示例**：给出一个 5 分的教科书案例，和一个 1 分的错误案例作为对照。

### 2. 难易度矩阵 (Difficulty Matrix)
**定义**：一个按照“题目难度”和“业务模块”交叉分布的测试计划表。
**比例建议 (2:5:3)**：
- **20% 简单 (Easy)**：模型闭着眼都能答对的基础常识（测底线）。
- **50% 中等 (Medium)**：需要多步推理或调用特定 API 的核心业务场景（测主力性能）。
- **30% 困难 (Hard)**：极端边界情况、极长上下文或复杂逻辑漏洞修复（测天花板高度）。
**价值**：防止模型通过“狂刷简单题”来虚报高分。

## 七、 P0 与长尾 Case 在你的项目中的映射

在不同项目中，这两种 Case 决定了产品的“下限”和“上限”。

### 1. 项目应用映射表

| 项目名称 | P0 级 Case (必考题/红线) | 长尾 Case (加分题/天花板) |
| :--- | :--- | :--- |
| **AI 代码助手 (招商局)** | 代码不能有 SQL 注入/明文密码；核心 API 调用必须正确。 | 处理极其生僻的遗留系统库；修复涉及 5 个文件以上的逻辑 Bug。 |
| **量化 Agent (WorldQuant)** | 策略必须符合止损逻辑；严禁出现“未来函数”或暴力拟合。 | 在极端行情（如熔断、崩盘）下的逻辑避险；多因子非线性合成策略。 |
| **智能客服 (BERT+RAG)** | 用户问退货策略告知正确地址；严禁回答违法违规或辱骂用户。 | 用户提出极其模糊的情绪化反馈；处理知识库中未覆盖的冷门促销政策。 |
| **医疗图像分割 (科研)** | 必须能准确识别出明显的病灶区域（不漏诊）。 | 对低对比度、形状极度扭曲或带有干扰背景的微小病灶进行精准切割。 |

### 2. 它们涉及到产品的哪些环节？

- **需求定义期**：PM 定义什么是 P0 需求（必须上线），什么是 P1/P2 长尾功能（以后再说）。
- **测试/评测期**：Benchmark 中 P0 必须 100% 通过；长尾 Case 用来评估模型“智力等级”。
- **风险控制期**：P0 代表合规和安全，是公司不被告、不赔钱的底线。
## 八、 P0 与 长尾 Case 的设计方法论 (Methodology)

作为 PM，设计 Case 不是拍脑袋，而是一套严谨的“选拔”机制。

### 1. P0 级设计：由果溯因 (Backward from Redlines)
- **业务红线法**：列出最坏的情况（如：代码被黑、用户隐私泄露、AI 辱骂客户）。这些“绝对不能发生”的场景就是 P0。
- **核心路径法**：列出 80% 用户每天都在用的功能（如：查订单、写一个简单的函数）。如果这些坏了，产品就失去了价值。

### 2. 长尾级设计：由内向外 (Forward from Edge cases)
- **日志挖掘法**：从线上千万条 Log 中抽取那些“模型无法回答”或“用户反复追问”的 Case。
- **对抗性测试 (Adversarial Testing)**：故意给模型出难题、设圈套（如：带语法错误的 Prompt、多重否定的逻辑题），看模型的韧性。

## 九、 企业级标准实践流程 (Corporate Workflow)

在成熟的 AI 公司（如字节、蚂蚁、商汤），Benchmark 的产生遵循**“自动化飞轮”**：

1.  **数据采集 (Collection)**：通过埋点和日志系统，将用户真实的对话、报错信息自动汇聚。
2.  **数据精选 (Curation)**：算法或 PM 使用聚类工具，去除掉重复的简单题，筛选出最具代表性的“考题”。
3.  **专业标注 (Labeling)**：在 **LabelStudio** 或内部平台上，分发给专家组进行“金标（Ground Truth）”标注。
4.  **基准库版本化 (Versioning)**：Benchmark 也是有版本的（如 v1.0, v2.1）。每当有新功能或新数据，都会更新版本，确保模型不断进步。
5.  **质量关卡 (Quality Gate)**：在 CI/CD 流程中设置卡点——模型评测不达标，代码分支就不允许合并上线。
## 十、 避坑指南：面试中的指标陷阱 (Trap Prevention)

面试官可能会问一些看似专业但带有陷阱的问题，你需要展现出对指标局限性的思考。

### 1. 为什么不能盲目相信 ROUGE/BLEU？
- **现象**：虽然分数高，但意思完全反了。
- **原因**：它们只看字符重合。例如：标准答案是“你应该去”，AI 回答“你不该去”。这两个句子 ROUGE 分极高，但逻辑完全错误。
- **面试对策**：承认它们在初期有参考价值，但强调在 LLM 时代，**“语义逻辑”** 远比 **“字符重合”** 重要。

### 2. 为什么 Cosine Similarity (余弦相似度) 用来评测不靠谱？
- **现象**：两个向量非常接近，但事实错误。
- **原因**：相似度只能证明它们在聊同一个话题，不能证明它的事实是否正确。
- **面试对策**：提倡使用 **Natural Language Inference (NLI)** 或者 **LLM-as-a-Judge** 来判断蕴含关系。

## 十一、 如何证明评测是靠谱的？(Human-AI Alignment)

面试官必杀问：“你怎么知道你的 GPT-4 裁判打分是准的？”

### 1. 人机对齐验证 (Human-AI Consistency)
- **做法**：从评测结果中随机抽取 10%-20%，让业务专家（人工）同步打分。
- **核心指标**：计算 **Cohen's Kappa 系数** 或 **Pearson 相关系数**。
- **标准**：如果相关性 > 0.8，说明机器已经基本对齐了专家的判断逻辑，这套自动化评测才是可信的。

### 2. 裁判 Prompt 的迭代
- 如果发现人机不一致，PM 需要去分析 Bad Case，更新评价 Prompt 中的评分标准（Criteria），直到机器打分和人工打分趋于一致。
