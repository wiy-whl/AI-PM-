# [专业工具] AI PM 场景定义模板 (Standard Scenario Case Card)

作为一个 AI PM，当你发现线上指标下跌或接到用户吐槽时，你的第一产出不应该是“代码”，而应该是这份**《场景定义卡片》**。它能让研发瞬间明白：我们要打什么样的仗。

---

## 📋 场景定义卡片 (Scenario Definition Card)

### 1. 场景基本信息 (Basic Identity)
*   **场景 ID / 名称**：[例如：Scenario_012_Private_RPC_Conflict]
*   **业务领域**：[例如：金融量化策略开发 / 跨语言转换]
*   **优先级 (Priority)**：P0 (核心业务堵死) / P1 (高频体验瑕疵) / P2 (长尾低频)

### 2. 特征描述 (Feature Attributes) —— 描述“考题”是什么样的
*   **上下文特征**：[例如：当前文件包含 500 行以上的历史代码，且涉及多个同名但版本不同的类库。]
*   **输入触发点**：[例如：用户在编写 `rpc_client.` 后停顿，期望补全具体的 API 方法名。]
*   **核心挑战点**：[例如：模型必须跳过本地 Context 中的 v1 干扰项，精准命中知识库（RAG）中的 v2 定义。]

### 3. 用户痛点与风险 (User Pain & Risk) —— 描述“为什么要修”
*   **用户侧表现**：用户点击采纳后，代码标红，需手动修改 5 分钟以上。
*   **业务负面影响**：导致该项目的采纳率从 65% 掉到 20%，引起了核心研发小组的投诉。

### 4. 评测/验收标准 (Eval & Acceptance Criteria)
*   **逻辑正确项**：必须精准补全为 `fetch_user_v2`。
*   **一票否决项**：如果出现了 `import com.old.version` 这种过期引用，直接判 0 分。
*   **性能底线**：在 8k Context 下，补全时延必须控制在 500ms 以内。

## 🚀 实战演示：针对你实习项目的案例 (Example)

| 字段 | 填充内容 (以 AI 插件为例) |
| :--- | :--- |
| **场景名称** | **“跨项目私有常量重用”场景 (Cross-Project Constant Reuse)** |
| **特征描述** | 工程目录下存在多个 Utility 项目，其中定义了同名的 `CONFIG_KEYS` 但属于不同部门。触发点是在代码补全时引用了 `GlobalConfig.get()`。 |
| **核心挑战** | 考查 RAG 检索的 **“路径感知能力 (Path Awareness)”**。模型不能只看名字，要看文件所属的真实层级。 |
| **用户痛点** | 之前模型老是引错包，导致代码虽然跑通了逻辑，但连到了错误的测试环境服务器。 |
| **评测标准** | 必须通过沙箱编译，且 `import` 路径必须完全指向受限的 `financial-core` 目录。 |

### 💡 如何在面试中发挥这个模板的威力？

当面试官问你：**“你是怎么确定要优化哪一部分性能的？”**

**你可以打开这个“锦囊”：**
> “我并不是凭感觉去优化的。我建立了一套 **『场景发现与定义体系』**。
> 
> 每当我们监控到指标异常，我会先进行归因，然后把这些 Bad Cases 提炼成名为 **『跨项目私有常量重用』** 的场景卡片（如上表）。
> 
> 我会拿着这张卡片去跟算法同学对：*『看，这是目前影响采纳率最严重的场景，背景特征是 X，验收标准是 Y。』*
> 
> 这样，我们后续的 **【AI 预评分】** 和 **【专家仲裁】** 就有了统一的参考系。这种**标准先行、数据驱动**的方式，让我们的迭代效率比之前提升了 30% 以上。”

**你可以尝试把你实习中遇到的一个真实 Bad Case，按照这个模板填一下。如果你填不出来，把情况告诉我，我陪你一起“提炼”出那个最值钱的场景名称！**
