## 二、面试逐字稿：当面试官问你“你是如何评测这个代码助手的？”

**(1. 打破刻板印象：定义我不是 QA，我是用评测找业务机会的 PM）**
“在做类 Cursor 项目时，我接手的核心任务是评估模型表现。但我首先向团队明确了一点：**我不是专业的 QA，我不为了找代码层面的 Bug 而评测；我是从产品视角切入，我的测试报告必须能直接指导 PRD 优化和模型调优。**
拿到需求后，我不盲测，而是先拆解 PRD 的商业指标：补全接受率要过 65%，用户满意度要超 7 分。我把这个大目标落到了一个 10 页的测试计划里：规定 20% 做主观手动测试，80% 靠自动化基线打分。”

**(2. 展现数据嗅觉：怎么搞测试数据？）**
“为了跑自动化，我必须有数据集。我不用开源的烂大街数据。
我去公司的代码库拉取了真实的 React Bug 案例，并进行了路径脱敏。更提效的是，我利用了 Claude 等高阶大模型，把 50 个手写 Case 用 Prompt 泛化成了 500 多个难度递进的变体，并用 LabelStudio 打上『语言/场景/难度』标签。这样我们的评测库就具备了绝对的**多样性和内网私有性**。”

**(3. 展现硬核动手能力：你是怎么‘算’分数的？ - 极高分段落）**
“在这个过程中，我不等研发给我排期，我**自己手写了 Python Runner 跑测脚本**。
我写了一个由 `requests` 构造的循环引擎，带上 `Prompt`、`Temperature` 等参数去批量请求腾讯混元 API，并做了 `sleep(1)` 的限速来防防熔断。

对于返回的代码，我不肉眼看，我定了一个**『四维判分标准』**：
1. **Pass@1**：最硬核的指标，拿生成的代码直接丢进 Pytest 跑，不报错才算过；
2. **编辑距离匹配**：针对简单的补全，我用 Python 的 `difflib/Levenshtein` 算相似度，只有相似度大于 80% 才算 Pass。
3. **幻觉与底线拦截**：我写了正则校验引擎，专门抓取它有没有编造公司不存在的 API (`fake_function`)；同时，对于高风险试探题，哪怕生成了可执行的代码，只要未达拒绝红线，在我这里直接判 0 分。”

**(4. 掌控大局观：收口闭环）**
“最后，自动化脚本跑出的‘客观分’，配合我通过内网问卷每天抓取统计的‘主观反馈分’汇拢。通过这两方数据，我在短短几周内驱动了产品进行了 3 轮核心迭代（比如加上了极其重要的 Diff 高亮功能）。把评测真正转化成了产品动能。”
