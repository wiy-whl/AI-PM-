## 🌟 简历中的“核武器”：技术型 AI PM 描述

**主要项目**：集团内部 AI 编程助手（类 Cursor 插件）评测体系构建
**核心职责**：

*   **【定义评测北极星指标】**：从业务视角拆解 PRD，定义了包含 **Pass@1（首位编译通过率）**、**自纠错挽回率**及 **NPS 用户满意度**在内的四维度评估基线。
*   **【构建自动化评测脚手架】**：独立编写 **Python 评测引擎 (Runner Script)**，实现对腾讯混元 API 的批量高并发请求。处理了 `max_tokens` 优化、`temperature` 随机性控制及 API 限速 (Rate Limit) 熔断机制。
*   **【多模态判分逻辑实现】**：摒弃单一字面匹配，采用 **Execution-based Eval (基于执行的评测)**。利用 Pytest 跑自动化单测，辅以 `Levenshtein` 编辑距离算法（阈值 >80%）及正则匹配（幻觉检测），实现客观分的精准刻画。
*   **【数据资产与 A/B 测试】**：利用 Hunyuan 辅以 Claude 生成 500+ 对抗性测试案例，通过 **A/B 测试 Prompt 变体**（保守 vs 激进），直接驱动了插件内 Diff 高亮显示等核心交互功能的迭代。

## 🗣️ 面试高分逐字稿：当面试官问“你做了什么？”

**(1. 点击痛点：从工程视角定义问题)**
“我在进入项目组后发现，大家对腾讯大模型在内部私有库上的表现缺乏‘客观标尺’。我作为一个 Technical AI PM，没有等研发排期，而是**自己动手建立了一套自动化评测流水线**。我首先审阅 PRD，将模糊的需求量化为：补全接受率 >65% 和修复成功率 >70%。”

**(2. 展现核心硬核：你是怎么做的？)**
“我最核心的活是写了一个 **Python 自动化 Runner**。我不仅要写代码通过 `requests` 调 API，还要关注底层细节：比如我把 `temperature` 设定在 0.5-0.7 之间平衡稳定性与创造力，并且在脚本里加了 `sleep()` 队列来应对高并发下的 `rate limit`。

对于结果，我采用了**三位一体的判分法**：
*   **代码级**：直接跑 Pytest，过不去单测的一律判错。
*   **文本级**：算编辑距离，只有相似度大于 80% 才算有效补全。
*   **产品级**：我利用正则抓取大语言模型常犯的『幻觉 API 错误』。这种硬核数据让我能直接拿着图表去对算法同学说‘这版模型在 Java 跨文件引用上翻车了’，让他们服气。”

**(3. 展现产品化思维：结果如何？）**
“随后我通过内网问卷收集了 3 轮反馈，通过 NPS 指标的变迁发现用户对生成的代码风格很敏感。于是我推动研发在插件中增加了 **Diff 高亮比对预览机制**。
最终，我不是在找 Bug，我是在用这套评测系统**寻找产品迭代的最佳机会点**。由于有了这套基准，我们内部插件的代码采纳率在三个月内提升了整整 X 个百分点。”

## 🧪 你的技术细节补全（供面试加分用）：

*   **Q: 遇到 API 限流怎么办？**
    *   **A**: “我在 Python 脚本里写了一个简单的重试策略和计时器，每分钟请求数控制在内部 Hunyuan 接口的 60 次以内，并在延迟监控中发现，当输入 context 超过 4k tokens 时，首字延迟会显著升高。”
*   **Q: 编辑距离用来测什么？**
    *   **A**: “主要测 Tab 键补全。如果 AI 建议的代码和用户最终手写的代码『编辑距离』极小，说明我们的补全精准度极高，这种统计比模糊的用户体感要有效得多。”
*   **Q: 为什么 A/B 测试要测 Prompt 变体？**
    *   **A**: “因为我发现‘保守派 Prompt’（强制模型只改一行）虽然 Pass@1 高，但用户觉得太鸡肋；‘激进派’虽然容易错，但一旦对了大块生成收益极高。我通过评测数据锁定了最终的动态平衡点。”
